# その言語を見たことのない読み手のために書く

*2026年10月29日*

公開されているコードが少ない若い言語では、その言語でコードを書くよう頼まれたモデルは、言語を見たことのない読み手になります。モデルはプログラムを書き、実行し、返ってきた結果を読み、書き直します。この読み手にとっては、この繰り返しが経験のすべてです。culebraの設計の多くは、この繰り返しの1周にいくらかかるか、という問いへの答えになっています。

このエッセイは、その設計判断と、いくつかの判断を数字で確かめようとした小さな実験について書きます。実験は小さく、そこから言えることは設計の意図より狭いです。以下の節では、この2つを分けて書きます。

## 1周にかかる費用

1周が高くつく原因は4つあります。実行速度の話ではありません。

**自信のある間違った推測。** 間違いやすいのは、ありふれた名前です。`sort`、`take`、`items`、`length`。どの言語にもありますが、綴りも引数の順も言語ごとに違います。5つの言語を見てきた読み手は、6つ目の言語でも、考えずに別の言語の書き方をします。問題になるのは珍しい機能の間違いではなく、ごく普通の呼び出しの間違いです。

**黙って進む失敗。** 未定義の名前はプログラムが始まる前に拒否されますが、存在しないプロパティはエラーにならず`nil`になります。`xs.length`は`nil`として読まれ、プログラムはそのまま進みます。検査が見るのは名前だけで、メンバーは見ません。culebraはこの選択の代価を払っていて、最も安い対処は読み手にはっきり伝えることです。書いたものは実行して確かめること。

**同じことの複数の書き方。** 条件で決まる値を4通りに書けると、モデルは1つのプログラムの中で4通りとも使い、読み手はどれが意図した書き方か判断できません。

**用意しなければならない環境。** マニフェスト、パッケージマネージャ、正しいモジュールを指さなければならない`import`。プログラム自体のロジックを試す前に、間違えうる場所です。

## 推測せず、引く

言語と標準ライブラリ全体のリファレンスはバイナリの中にあります。そのため、実行しているビルドと常に一致します。

```text
culebra docs -g 'Math.wrap'          print the sections that match
culebra docs -g '<name>' >/dev/null  exits 1 when nothing matches
culebra docs stdlib Scene            print one namespace's chapter whole
```

終了コードは`grep`と同じで、何か出力したら0、何も一致しなければ1です。プログラムやエージェントは「これは存在するか」を、何も読まずにはい・いいえで知ることができます。`-g`で見つからないシグネチャは、存在しません。

下の実験から、ここで1つ紹介します。案内を何も渡さず、`docs`コマンドも拒否する条件では、10試行のすべてが、少なくとも1回は自分から`culebra docs`を試しました。合計15回で、すべて拒否されています。このコマンドの存在は誰も伝えていません。この実験では、知らないコマンドラインツールに出会ったモデルは、まずそのツールに尋ねました。

## プロンプトに収まる1つのファイル

リファレンス全体は約150,000トークンあります。10行の関数を書くために読むには多すぎます。そこで`culebra docs quick-guide`が、そのための1つのファイルを出力します。構文、言われなくても使うシグネチャ、他の言語の習慣のうち持ち込めないものの表です。出力は約42KBです。

中身より大事な判断が2つあります。

*新しく文章を書かない。* 手で書いたAPIの要約は、真実の3つ目のコピーになり、最初に古くなります。手引きのシグネチャ索引は、リファレンスから`just gen-quick-guide`で生成します。中のコードブロックはすべて`culebra test --doc`で実行するので、戻り値を述べる行は、実際の呼び出しと照合されます。

*表は失敗の一覧にする。* 各行は、culebraでは失敗する、または黙って別のものになる習慣です。出力のための`puts`、比較関数を渡す`xs.sort(|a, b| ...)`、`xs.take(n)`、`s.ljust(10)`、同じスコープでの`x = 1`の2回目など。各行には、その習慣が何で、代わりに何を書くかが書いてあります。

プロジェクトの指示ファイルを読むエージェントには、[`agent.md`](../agent.ja.md)が短い形です。`CLAUDE.md`や`AGENTS.md`に追記する数行で、実行のしかた、調べ方、最初に手引きを読むこと、書いたものを実行することを伝えます。

## エラーは次のプロンプトになる

モデルの次の動きは、最後に読んだ行で決まります。そのためエラーは、読み手が必要とする3つを伝えなければなりません。どんな種類の失敗か、何が起きたか、どこで起きたか。culebraのexecutor、`--jit`、AOTは、同じプログラムに対して同じ種類、同じ文面、同じ位置を返します。この一致はプロジェクトの設計要件ですが、この読み手にとっては別の使い道もあります。プログラムをどの方法で実行したかによって、メッセージが変わらないことです。

構文エラーは、パーサライブラリが整形した文字列をそのまま通さず、フロントエンドが組み立てます。`x = [1, 2`は、38個の候補の一覧ではなく`expecting ',', ']' or an operator.`と言います（[`internals/frontend.md`](../internals/frontend.ja.md)）。

## 小さな実験でわかったこと

**設定。** 課題は5つです。それぞれ関数1つか2つと、隠したテストでできています。単語の数え上げ、JSONの集計、逆ポーランド式の評価、2つのgenerator、桁をそろえた文字表の描画。条件は3つで、各10試行（5課題を2回ずつ）です。

- **A。** 課題と`culebra`バイナリだけを渡す。`docs`コマンドは拒否される。
- **B。** Aに加えて、最初に読むファイルとして手引きを渡す。`docs`コマンドは拒否される。
- **C。** Aに加えて、プロジェクトの規則として`agent.md`の中身を渡す。`docs`コマンドは使えるので、手引きはコマンド1つで読める。

1試行は、新しい`sonnet`エージェントが専用のディレクトリで課題を解くことです。バイナリは何度でも実行できます。バイナリはラッパーで、呼び出しのたびに、最初のエラー行とともにログへ書きます。以下の回数はこのログから出しました。採点は、最終ファイルの末尾に隠したテストを足して行いました。その後、すべての記録について、試行のディレクトリの外を読んでいないかを調べました。30試行のどれも、リポジトリのドキュメントやソースには触れていません。

隠したテストは、課題ごとに2通りで確かめました。参照解答は通り、わざと壊した版は落ちます。

**結果。**

| | A: 何もなし | B: 手引き、引けない | C: 規則と引く手段 |
|---|---|---|---|
| 隠したテストに合格 | 10回中10回 | 10回中10回 | 10回中10回 |
| プログラムを走らせた回数、中央値（範囲） | 14.5（3〜39） | 1.5（1〜3） | 2（1〜3） |
| 一度も失敗しなかった試行 | 10回中0回 | 10回中7回 | 10回中5回 |
| プログラムを1回しか走らせなかった試行 | 10回中0回 | 10回中5回 | 10回中3回 |

どの条件でも、すべての試行が正しいプログラムで終わりました。バイナリがあって、やり直せるモデルは、そこまでたどり着きます。条件による違いは、そこに至るまでの回数です。モデルだけで解いたときは約15回、手引きがあったときは1〜2回でした。

条件Aで最初に失敗した理由は、3種類に分かれました。3試行は`ImmutableError`で、`mut`なしで束縛した名前に代入したものです。3試行は未定義の名前で、`puts`、`str`、単独の`sort`でした。4試行は構文エラーで、1つは`var`宣言でした。そのあとの失敗には、Arrayへの`xs.take(n)`、`sort_by`に渡した比較関数、`.length`がありました。これらの多くは、手引きの習慣の表にある行です（`puts`、比較関数、`take`、`.length`、2回代入した名前）。`str`と`var`は表にありません。

BとCは、この規模では差が出ませんでした。プログラムを走らせた回数は、Bが1.7回、Cが1.9回です。引くコマンドはCのすべての試行で使われ、10試行で合計46回でした。引いても何も見つからないことがあり（`ljust`、`pad_left`）、その試行も最後まで終わりました。

**この実験でわからないこと、弱い点。**

- *課題は、手引きを読んだ直後の人が書きました。* 課題のうち2つは、手引きが述べていることを試しています。文字列の文字数での幅は`size()`ではないこと、そして詰め物のための書式指定です。手引きのある条件に有利に働き、BとCが近く見える理由の大半は、おそらくこれです。
- *条件ごとに10試行、モデルは1つ、1回の作業。* 条件Aのばらつきは大きく（3回から39回）、BとCの間に見えた程度の差は、やり直しても保たれないでしょう。
- *課題は10〜30行です。* 1,000行のプログラムや、手引きがカバーしないライブラリについては、何も言えません。後者は`culebra docs -g`が効くはずの場面ですが、この実験では見ていません。
- *「走らせた回数」は代わりの指標です。* 数えているのは設計が問題にしている繰り返しの回数であって、利用者が1回ごとに払う費用ではありません。
- *比較の基準がありません。* モデルがよく知っている言語で同じ課題を解かせていないので、culebraをそれと比べてどうかは言えません。

裏付けられているのは、設計の意図より小さいことですが、そのまま言っておく価値があります。この課題では、手引きを渡されたモデルは約2回の実行で正しいプログラムを書き、渡されなかったモデルは約15回かかりました。

## 例が教えること

慣用的でない出力に対して、最初に思いつくのは規則を増やすことです。その方針を変えたのは、examplesの測定でした。2026年7月30日、ある整理の前には、`examples/`のプログラムは`.empty()`を0回しか呼ばず、`.size() == 0`か`> 0`を23回書いていました。コードから学ぶ読み手は「`empty()`は存在しない」と結論しますし、示された証拠からすれば、その結論は正しいのです。当時の手引き（`llm.md`。数日後に`quick-guide.md`へ改名）の例にも同じ習慣があり、しかもテストで実行されるので、権威があるように見えました。

直したのは規則ではなく例です。変更の後、`.empty()`は23回、長い形は0回になりました。その後に例が増えた現在の数は、147と42です。得た教訓は、例はコピーされもする規則だ、ということです。

## 同じことの書き方を減らす

いくつかの判断は、選択肢を減らすことだと読むと、恣意的に見えなくなります。

- パイプライン演算子はありません。メソッドをつなげれば足りるからで（統一された呼び出し構文により、どの関数も`x.f()`と呼べます）、プロジェクトが省いた理由として記録しているのはこれです。
- Setは`Set(a, b)`とだけ書きます。波括弧はObjectのものです。
- `culebra fmt`には書式のオプションがありません。
- マニフェストはなく、標準ライブラリに`import`は要りません。

どれも「1つの書き方が最良の書き方だ」という主張ではありません。背景にある考えは、2つの書き方から選ばなければならない読み手は、間違って選びうる、ということです。これは実験では試していません。

## 測っていないこと

生成した署名索引は、手で書いたものより効くのか。エラー文があるかどうかでなく、その書式が次の動きを変えるのか。訓練でこの言語を見たモデルは、今回試したモデルと違う動きをするのか。数時間続くセッションでは、これらはどうなるのか。どれも調べる方法はありますが、まだ調べていません。

## 系譜

この多くは、他の人のツールから学びました。`go doc`と`man`は、リファレンスを読み手がすでにいる場所、つまりコマンドラインに置きました。`gofmt`は、書式のオプションのない整形ツールが、議論を移すのではなく終わらせることを示しました。Elmとrustcは、エラーが何を期待していたか、どこで起きたかを述べることを当たり前にし、親切なメッセージはおまけではなく製品の一部だと示しました。Pythonの`help()`は、名前が何を意味するかを言語自身に尋ねる、もっと古い形です。このエッセイが足すのは小さなことです。終了コードではい・いいえを答える引き方、生成して実行する手引き、そして、その言語を見たことのない読み手に渡して案内を確かめる習慣です。
