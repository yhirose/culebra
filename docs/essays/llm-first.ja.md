# その言語を見たことのない読み手のために書く

*2026年10月29日*

これだけ若い言語には公開されたコードが少ないので、それを書くよう頼まれた
モデルは、その言語を見たことのない読み手です。モデルはプログラムを書き、
実行し、返ってきたものを読み、また書き直します。その読み手にとっては、この
ループが経験のすべてです。culebraの設計の多くは、このループの1回に何が
かかるかという問いへの答えです。

このエッセイは、その設計判断と、そのうちいくつかを数字にしようとした小さな
実験について書きます。実験は小さく、そこから言えることは、設計の意図より
狭いものです。以下の節では、その2つを分けて書くようにしています。

## ループの1回で、言語が何を請求するか

1回を高くするものは4つあり、速さの話ではありません。

**自信を持った間違った推測。** 間違いやすいのは、ありふれた名前です。
`sort`、`take`、`items`、`length`。どの言語にもあり、綴りも引数の順も言語ごとに
違い、5つの言語を見てきた読み手は、6つ目の言語の名前を、考えずに別の言語の
書き方で書きます。問題になるのは、珍しい呼び出しではなく、ごく普通の呼び出しの
間違いです。

**自分から知らせない失敗。** 未定義の名前はプログラムが始まる前に拒否されます
が、存在しないプロパティはエラーでなく`nil`なので、`xs.length`は`nil`として
読まれ、プログラムはそのまま進みます。検査が見るのは名前であって、メンバーでは
ありません。culebraはこの選択の代価を払っており、一番安い対処は、読み手にはっきり
伝えることです。書いたものを実行すること。

**1つのことを言う複数の書き方。** 条件で決まる値を4通りに書けるなら、モデルは
1つのプログラムの中で4通りとも使い、読み手はどれが意図した書き方か判断できません。

**組み立てるべき環境。** マニフェスト、パッケージマネージャ、正しいモジュール
を指さなければならない`import`。どれも、プログラム自身のロジックを試す前に間違え
られる場所です。

## 推測せず、引く

言語と標準ライブラリ全体のリファレンスはバイナリの中にあるので、いま実行している
ビルドといつも一致しています:

```text
culebra docs -g 'Math.wrap'          print the sections that match
culebra docs -g '<name>' >/dev/null  exits 1 when nothing matches
culebra docs stdlib Scene            print one namespace's chapter whole
```

終了コードは`grep`と同じです。何か出力したら0、何も一致しなければ1です。
プログラムやエージェントは「これは存在するか」と尋ね、何も読まずに、はいか
いいえを得られます。`-g`で見つからない
シグネチャは存在しません。

下の実験の観察を1つ、ここに置きます。モデルに案内を何も渡さず、`docs`コマンドも
無効にした条件で、10回の実行のすべてが、少なくとも1回は自分から`culebra docs`を
試しました。合計15回で、すべて拒否されました。そのコマンドがあることは誰も伝えて
いません。この実行では、知らないコマンドラインツールに出会ったモデルの最初の動きは、
ツールに尋ねることでした。

## プロンプトに収まる1つのファイル

リファレンスは約150,000トークンあり、10行の関数を書くためにモデルが読む量
としては多すぎます。`culebra docs quick-guide`は、そのための1つのファイルを
出力します。構文、言われなくても使うことになるシグネチャ、そして他の言語から
持ち込めない習慣の表です。出力されるテキストは約42KBです。

中身より大事な判断が2つあります。

*新しい散文ではない。* 手で書いたAPIの要約は、真実の3つ目のコピーになり、一番
先に古くなります。手引きのシグネチャ索引はリファレンスから`just gen-quick-guide`
で生成され、中のコードブロックはすべて`culebra test --doc`で実行されるので、
呼び出しの戻り値を述べる行は、その呼び出しと照合されます。

*表は失敗の一覧です。* 各行は、culebraでは失敗するか、黙って別のものになる習慣
です。出力のための`puts`、比較関数を渡す`xs.sort(|a, b| ...)`、`xs.take(n)`、
`s.ljust(10)`、同じスコープでの`x = 1`の2回目。行には、その習慣が何で、代わりに
何を書くかが書かれています。

プロジェクトの指示ファイルを読むエージェントには、[`agent.md`](../agent.ja.md)が
短い形です。`CLAUDE.md`や`AGENTS.md`に追記する数行で、実行のしかた、引き方、
最初に手引きを読むこと、書いたものを実行することを述べます。

## エラーは次のプロンプトである

モデルの次の動きは、最後に読んだ行で決まります。だからエラーは、読み手が要る3つ
を運ばなければなりません。どんな種類の失敗か、何が起きたか、どこで。culebraの
executor、`--jit`、AOTは、同じプログラムに対して同じ種類、同じ文面、同じ位置を
返します。この一致はプロジェクトの設計要件ですが、この読み手にはもう1つ使い道
があります。プログラムをどの方法で走らせたかに、メッセージが依存しないことです。

構文エラーは、パーサライブラリが整形した文字列を通すのでなく、フロントエンドが
作ります。`x = [1, 2`は、38個の候補のリストではなく
`expecting ',', ']' or an operator.`と言います
（[`internals/frontend.md`](../internals/frontend.ja.md)）。

## 小さな実験が示したこと

**設定。** 5つの課題。それぞれ1つか2つの関数と、隠したテストです。単語の
数え上げ、JSONの集計、逆ポーランド式の評価、2つのgenerator、揃えた文字の表の
描画。3つの条件で、各10回（5課題を2回ずつ）:

- **A。** 課題と`culebra`バイナリだけ。`docs`コマンドは拒否される。
- **B。** Aに加えて、先に読むファイルとしてquick-guide。`docs`コマンドは拒否される。
- **C。** Aに加えて、プロジェクトの規則として`agent.md`の中身。`docs`コマンドは
  使えるので、手引きはコマンド1つの先にある。

どの実行も、新しい`sonnet`エージェントが専用のディレクトリで行い、バイナリは何度
でも実行できました。バイナリはラッパーで、呼び出しごとに、その最初のエラー行と
ともにログへ書きました。以下の回数はこのログから出しています。採点は、最終ファイル
の末尾に隠したテストを足して行いました。そのあと全部の記録について、実行の
ディレクトリの外を読んでいないかを調べ、30回のどれもリポジトリのドキュメント
やソースに触れていませんでした。

課題ごとの隠したテストは、2通りで確かめました。参照解答は通り、わざと
壊した版は落ちます。

**結果。**

| | A: 何もなし | B: 手引き、引けない | C: 規則と引く手段 |
|---|---|---|---|
| 隠したテストに合格 | 10回中10回 | 10回中10回 | 10回中10回 |
| プログラムを走らせた回数、中央値（範囲） | 14.5（3〜39） | 1.5（1〜3） | 2（1〜3） |
| 一度も失敗しなかった実行 | 10回中0回 | 10回中7回 | 10回中5回 |
| 実行が1回で済んだ実行 | 10回中0回 | 10回中5回 | 10回中3回 |

どの条件のどの実行も、正しいプログラムで終わりました。バイナリがあり、やり直せる
モデルは、そこまで行き着きます。条件の間で違ったのは、そこに至るまでの回数です。
モデルが自力だったときは約15回、手引きがあったときは1〜2回でした。

条件Aの実行で最初に失敗した理由は、3種類に分かれました。3回は`ImmutableError`
で、`mut`なしで束縛した名前に代入したものです。3回は未定義の名前で、`puts`、
`str`、単独の`sort`でした。4回は構文エラーで、うち1回は`var`宣言でした。その
あとの失敗には、Arrayへの`xs.take(n)`、`sort_by`に渡した比較関数、`.length`が
ありました。これらの多くは手引きの習慣の表にある行です（`puts`、比較関数、`take`、
`.length`、2回代入した名前）。`str`と`var`は、表にありません。

BとCは、この規模では差が出ませんでした。実行回数は1.7回に対して1.9回です。
引くコマンドはCのすべての実行で使われ、10回で合計46回でした。引いても何も見つ
からない場合（`ljust`、`pad_left`）もあり、そのときも実行は最後まで終わりました。

**この実験が示していないこと、弱い点。**

- *課題は、手引きを読んだばかりの人が書きました。* 課題のうち2つは、手引きが
  述べることを試しています。文字列の文字数での幅は`size()`ではないこと、そして
  詰め物のための書式指定です。手引きのある条件に有利に働き、BとCが近く見える
  理由の大半はおそらくこれです。
- *条件ごとに10回、モデルは1つ、1回の作業で。* 条件Aのばらつきは大きく（3回から
  39回）、ここで見えたBとCの差の大きさは、やり直すと保たれないでしょう。
- *10〜30行の課題です。* 1,000行のプログラムについても、手引きが覆わない
  ライブラリについても、何も言えません。後者は`culebra docs -g`が効くはずの所
  ですが、この実験はそこを見ていません。
- *「走らせた回数」は代理の指標です。* 数えているのは、設計が問題にしている
  ループの回数であって、利用者が払う1回あたりの費用ではありません。
- *基準がありません。* モデルがよく知っている言語で同じ課題を行わなかったので、
  culebraをそれと比べてどうかは何も言えません。

裏付けられているのは、設計の野心より小さいことで、そのまま言っておく価値が
あります。この課題では、手引きを渡されたモデルは約2回の実行で正しいプログラムを
書き、渡されなかったモデルは約15回で書きました。

## 例が教えること

最初に考えるのは、慣用的なCulebraの規則を書くことです。その方針を変えたのは、
examplesの測定でした。2026年7月30日、ある整理の前には、`examples/`のプログラムは
`.empty()`を0回呼び、`.size() == 0`か`> 0`を23回書いていました。コードから学ぶ
読み手は`empty()`が存在しないと結論し、示された証拠からすれば、その結論は正しい
のです。当時の手引き（`llm.md`。数日後に`quick-guide.md`へ改名されました）の例も
同じ習慣を持っており、テストで実行されているので、権威があるように見えました。

直したのは規則でなく例です。変更の後、`.empty()`は23回、長い形は0回になりました。
その後に例が増えた今の数は、147と42です。得た教訓は、例は、コピーもされる規則
だということです。

## 同じことを言う書き方を減らす

いくつかの判断は、選択肢を減らすことだと読むと、恣意的に見えなくなります。

- パイプライン演算子はありません。メソッドをつなげれば足り（統一された呼び出し
  構文により、どの関数も`x.f()`と呼べる）、プロジェクトが省いた理由として記録
  しているのはこれです。
- Setは`Set(a, b)`と書き、ほかの書き方はありません。波括弧はObjectのものです。
- `culebra fmt`には書式のオプションがありません。
- マニフェストはなく、標準ライブラリに`import`は要りません。

どれも、1つの書き方が最良の書き方だという主張ではありません。考え方の背景は、
2つの書き方から選ばなければならない読み手は、間違って選びうる、というものです。
これは実験では試していません。

## 測っていないこと

生成した署名索引は、手で書いたものより効くのか。エラー文の有無でなく書式が、次の
動きを変えるのか。訓練でこの言語を見たモデルは、試したモデルと違う動きをするか。
数時間続くセッションで、これらはどうなるか。どれも方法のある問いで、どれもまだ
尋ねていません。

## 系譜

この多くは、他の人のツールから学びました。`go doc`と`man`は、リファレンスを
読み手がすでにいる場所、コマンドラインに置き、`gofmt`は書式のオプションのない整形
ツールが議論を移すのでなく終わらせることを示しました。Elmとrustcは、エラーが
何を期待していたか、どこでかを述べることを期待として定着させ、親切なメッセージは
おまけでなく製品の一部だと示しました。Pythonの`help()`は、名前が何を意味するかを
言語自身に尋ねる、もっと古い形です。このエッセイが足すのは小さなものです。終了
コードがはい・いいえを言う引き方、生成して実行する手引き、そして、その言語を
見たことのない読み手に渡して案内を確かめる習慣です。
