# アンダース・ヘルスバーグの並行処理論とculebra

*2026年8月1日*

2009年にO'Reillyから出版された『Masterminds of Programming』（Federico Biancuzzi、
Shane Warden編。邦訳『言語設計者たちが考えること』オライリー・ジャパン、2010年）の
第13章「C#」に、アンダース・ヘルスバーグ（C#、のちにTypeScriptの設計者）が
並行処理をどう扱うべきかについて語った一節がある。インタビュー自体は出版より
前に行われているので、発言があったのはもう少し早い、2000年代後半のどこかだろう。
以下は邦訳からの抜粋にもとづく要約で、逐語訳ではなく、要点を私なりに並べ直した
ものだと理解してほしい。

- 命令型プログラミングは副作用に依存しているので、`/Parallel`のようなコンパイラ
  スイッチひとつで自動的に並列化される、というようなことは起きない。人々は
  実際に試みたが、C++・C#・Javaのような主流の命令型言語ではうまくいかなかった。
- そこに到達するには、少なくとも二つのハードルがあるという。まず、スレッド・
  ロック・モニタよりもレベルの高い、近代的な並行処理APIが要る。次に、そういう
  プログラミングスタイルを簡単かつ安全に行えるようにする必要がある — オブジェクト
  の不変性を保証したり、副作用のない純粋関数を用意したり、オブジェクトグラフの
  独立性を分析したり（あるグラフへの参照が他と共有されていないかをチェックし、
  共有されていなければ他に影響を与えずに変更できると判断する）。これはコンパイラの
  分析によって、既存の型安全性やメモリ安全性とよく似た安全性を提供できるはずだ、と
  見通している。
- 特定の分野（データ変換、数値処理、信号処理、画像処理など）に精通した人たちが、
  内部的には大規模な並行性を実現しているのに、外からは同期的に見えるAPIを
  書けるようにする — いわば並行性をAPIの内側に囲い込む、という道筋も語っている。
- データパラレル型の処理には、「データはここです、行ってほしい演算はこれです、
  使えるだけのCPUを使ってできる限り高速にやってください」と言えるような高レベル
  APIモデルが向いている、とも述べている。あわせて、APIに渡すコード片（ラムダ式）
  をコンパイラが分析し、副作用がないことを保証したり警告したりしてくれるとよい、
  という話もしている。
- 最後に、これは並行性のごく一部の話だと自ら断ったうえで、Erlangのような、非同期
  エージェントとメッセージパッシングに基づくかなり毛色の違うプログラミング
  モデルが、スケーラビリティの高い分散システムですでに使われていることにも触れて
  いる。

それから15年あまりが経ったいま振り返ってみると、彼の見立てはかなりの部分で
的中していたように見える。自動並列化の魔法は結局起きなかった。もう少し込み入っているのが「近代的な
高レベルAPI」の中身で、async/awaitと構造化並行処理が主要言語に定着した一方、
RustとSwiftはまったく別の軸 — コンパイル時の安全性保証 — を切り開いた。この
二つが本当に彼の思い描いた「スレッド・ロック・モニタを超える何か」と同じものなのかは、
そう単純には言い切れない気がしていて、この点は後段でも触れる。

このエッセイでは、その見立てを物差しにしてculebraの並行処理設計を眺めてみたい。
culebraの並行モデルは「隔離単位（プロセス/isolate）+ コピー境界 + channel」という
形をしていて、共有可変ヒープを言語として提供しない。以下、典型的な並列コードを
5つ挙げながら、それぞれがヘルスバーグの発言のどのあたりに位置づけられそうかを
見ていく。

## 例1: agent glue — `Proc.all`（プロセス並列と部分失敗）

```culebra
# doctest: skip
# 3つのLLMプロバイダに同じプロンプトを並列で投げ、全結果を回収する
let results = Proc.all([
  ["llm-cli", "--provider", "openai",    prompt],
  ["llm-cli", "--provider", "anthropic", prompt],
  ["llm-cli", "--provider", "google",    prompt],
], limit: 3, timeout: 30000)

for r in results {
  if r.ok { println(r.stdout) } else { println("failed: " + r.stderr) }
}

# 最速の1個だけ欲しいなら
let fastest = Proc.race([cmd_a, cmd_b, cmd_c])
```

「スレッド・ロック・モニタよりレベルの高いAPI」の要求に対しては、いちばん手堅い
答え方になっている。スレッドどころか共有メモリ自体が存在せず、OSがプロセス境界で
独立性を保証してくれる。面白いのは戻り値が例外でなく`ok`フラグ付きの結果配列
（JSの`Promise.allSettled`に近い意味論）になっていて、「3つ走らせて2成功1
失敗」という部分失敗をふつうの値として扱えることだ。単一例外モデル（一個の失敗で
全体を巻き戻すtry/catch）は並行の部分失敗をうまく表現できない — culebraは
最初からそこを避けるように設計されている。このallSettled的な割り切りは、Erlangのlet-it-crash哲学に近い
発想でもあり、彼が「ごく一部の話」と留保しつつ触れたメッセージパッシングの世界の
考え方が、プロセス並列という別の場所にも滲み出している。

## 例2: データパラレル — `Parallel.map`

```culebra
# doctest: skip
# 「データはここ、演算はこれ、使えるCPUで速くやってほしい」（意訳）
let thumbs = Parallel.map(image_paths, |p| make_thumbnail(p), limit: 8)

# 進捗表示つき・全件走り切り版
let settled = Parallel.map_settled(urls, |u| Http.get(u).body,
    on_progress: |done, total| IO.print("\r" + done.to_string() + "/" + total.to_string()))
```

これはデータパラレル処理について彼が語った「データはここ、演算はこれ、使える
CPUを使ってできる限り高速にやってほしい」という高レベルAPIモデルを、かなり
忠実になぞっている。加えて`limit: 8`のような呼び出しの裏ではworker poolが動いていて、
呼び出す側からは「並列で走った結果がまとめて返ってくる」という、ほとんど同期
呼び出しと変わらない形になっている。これは彼が語っていた、特定分野の専門家が
並行性をAPIの内側に囲い込む、という道筋にかなり近い。

ただし、APIに渡すラムダをどう安全にするかという部分は、彼の想定とはだいぶ
違う経路を通っている。彼は、APIに渡されたコード片（`|p| make_thumbnail(p)`の
ようなラムダ）をコンパイラが分析し、副作用がないことを保証したり警告したり
してくれることを望んでいた。culebraがやっているのは、そういう分析ではなく
**構築による独立性の確保**である。このラムダはspawnの瞬間にシリアライズ
され、各workerは自分専用のコピーされたオブジェクトグラフを受け取る。独立性は
コンパイラが証明するものではなく、コピーによって自動的に成り立ってしまう。彼が
コンパイラに期待していた「副作用がないことの保証」は、culebraでは実行時の境界
検査（Sendable検査、違反は`SendError`）1点に縮んでいる。値がグラフとして交差
していないかを静的に解析するより、境界を越える値だけをそのつど検査するほうが
ずっとやさしく、動的型の言語でも実装できる — これは彼が思い描いていた解とは
別の道で、同じ問いに対する一つの回答になっている。

## 例3: メッセージパッシング — `Channel`と`fan_in`

```culebra
# doctest: skip
# producer-consumer: パースを別isolateに逃がし、本体はストリームを消費する
let (tx, rx) = Channel.new(64)
let prod = Isolate.spawn(fn () {
  for line in File.open("big.log").lines() { tx.send(parse(line)) }
})   # isolate終了でtxがdrop → channel自動close → for-inが終わる

for record in rx { index.add(record) }
prod.join()

# fan-in: worker N本のストリームを1本に合流する
let merged = Channel.fan_in(shards, fn (shard, tx) {
  for hit in search(shard, query) { tx.send(hit) }
})
for hit in merged { report(hit) }
merged.join()
```

ヘルスバーグはErlang的なメッセージパッシングを、あくまで分散システムの世界で
すでに使われている一例として、しかも「これは並行性のごく一部の話だ」と自分から
留保しつつ語っていた。culebraではこの位置づけが変わっていて、分散システム向けの
傍流ではなく、同一プロセス内の既定の通信手段になっている。共有ヒープを提供しない以上、メッセージパッシングは
選択肢のひとつではなく、唯一の通信手段になってしまうからだ。もうひとつの違いは、
Erlangのmailbox（PID宛て）ではなく、Go / Rust系のCSP channel（パイプ中心）を
選んでいることだ。

そして地味だけれど案外いちばん効いているのが、`send` / `recv`がblockingで
「色」がついていないことだ。isolateは本物のスレッドなので、blocking
してもかまわない。この15年あまり主流だったasync/await（関数にasyncという
色が付き、呼び出し側に伝播していく）を導入せずにこのコードが書けるのは、その
構造のおかげだ。冒頭で少し触れたとおり、async/awaitが彼の言う「近代的な高レベル
API」の実現形かどうかは実は微妙で、JavaがCompletableFutureからLoomの
virtual thread（色なしのblockingへの回帰）に舵を切ったことは、async/awaitが
唯一の答えではなかったことの傍証のように見える。auto-close（送信側が異常終了
しても受信側のfor-inは必ず終わる仕組み）は、ヘルスバーグが名指ししなかった
けれど実運用ではけっこう致命的な、部分失敗がデッドロックに化ける問題への言語側の
答えになっている。

## 例4: 共有メモリの生き残り方 — `@packable`と`SharedBuffer`

```culebra
# doctest: skip
@packable class Particle { x: Float32; y: Float32; vx: Float32; vy: Float32 }
let world = SharedBuffer.new(100000, Particle)

# 各workerが互いに素な範囲だけ書く — 同期ゼロ、コピーゼロ
let chunk = 12500
Parallel.each(iota(0, 8), fn (w) {
  for i in (w * chunk)..((w + 1) * chunk) {
    world[i].x = world[i].x + world[i].vx
    world[i].y = world[i].y + world[i].vy
  }
})

# 本当に同じセルを触るときだけ、唯一のロックが登場する
@packable class Counter { n: Int64 = 0 }
let tally = SharedBuffer.new(1, Counter)
Parallel.each(iota(0, 8), fn (w) {
  tally.with_lock(fn () { tally[0].n = tally[0].n + 1 })
})
```

`world[i].x = world[i].x + world[i].vx`という行は、見た目はただのフィールド代入
にすぎない。だが裏ではisolate境界をまたいだzero-copyの共有が起きている —
これは彼が語っていた「並行性をAPIの内側に囲い込み、外からは同期しているように
見える」という道筋の、かなり具体的な実現になっている。ユーザーはworkerが互いに
素な範囲を書いていることさえ意識すれば、あとは配列の要素にふつうに代入している
だけだ。

もうひとつ、ここは彼が語っていた「オブジェクトグラフの独立性分析」というハードル
への応答にもなっている。あるグラフへの参照が他と共有されていないかをコンパイラが
チェックする、という彼の発想を、culebraはデータの形のほうに落とし込んでいる —
`@packable`は「ポインタを含まない固定レイアウト」であることを宣言する制約で、
ポインタがなければそもそもグラフが存在せず、グラフがなければ独立性分析の対象
自体が消えてしまう。要素がdisjointであるという独立性は、型検査ではなく
インデックスの算術という、誰にでも見て確かめられる形で表現されている。問いの
立て方そのものは彼が示したとおりで、答え方だけが違う、という感じに近い。

ロックの扱いにも注目したい。culebraにはMutexという第一級の値は存在せず、
`with_lock`は共有が実在する唯一の構造（SharedBuffer）に付随する、スコープ
付きのメソッドとしてしか現れない。彼は「スレッド・ロック・モニタよりレベルの
高いAPIが要る」と述べていたが、culebraの答えはそのうちモニタ（データと
ロックを一体化する発想、Concurrent Pascalに遡る）を思わせる作りで、「ロックより
高レベルなAPI」という要求を、ロックを消すのではなく、ロックをデータに縛りつける
ことで満たしている。

## 例5: 不変性の保証 — `Shared.new`

```culebra
# doctest: skip
# 巨大read-onlyデータを全workerで1コピー共有する（RustのArc<T>相当）
let model = Shared.new(load_weights())
let vocab = Shared.new(JSON.parse(FS.read("vocab.json")))

let outs = Parallel.map(batches, fn (b) {
  infer(model, vocab, b)     # 全workerが同じ凍結ツリーを読む。コピーなし
})
# vocab["hello"] = 1  →  ImmutableError（全書き込み面が実行時に拒否される）
```

ヘルスバーグはハードルの筆頭に「オブジェクトの不変性の保証」を挙げていて、
それをコンパイラの仕事だと想定していた。C#は`readonly` / `init` / recordと
型のレベルで少しずつ前進してきたけれど、推移的で深い不変性にはまだ届いて
いない（recordの中のListは今も自由に変更できる）。culebraの答えは、不変性を型の性質ではなく
値の性質として扱うことだ — `Shared.new`は値のツリー全体を推移的に凍結し、
それ以降のあらゆる書き込みが実行時に`ImmutableError`として拒否される。静的な
保証（Rustの`&`）には及ばないが、C#が15年あまりかけてもまだ手にしていない、
深く・推移的で・逃れようのない不変性を、動的検査という別のコストを払うことで
手にしている、とは言えそうだ。

しかも凍結のための走査は、isolateを越境するときのシリアライズとまったく
同じコードを使っている。だから「不変であること」と「共有してよいこと」が、
定義のレベルで一致している。SendとSyncを別のtraitにしたRustより粗い
やり方だけれど、それなりに筋の通った単一の原理になっている。

## まとめ: ヘルスバーグの発言のどこにculebraは立っているか

| 彼の発言 | culebraの対応 | 手段の違い |
|---|---|---|
| スレッド・ロック・モニタより高レベルなAPI | `Proc.all` / `Parallel.*` / `Channel` — thread / lock / monitorは表層に現れない | 抽象化というより削除に近い（lockはSharedBufferに付随する1箇所だけに封じ込め） |
| 不変性・純粋性・オブジェクトグラフ独立性へのコンパイラ支援 | Sendable境界検査 + `Shared.new`の凍結 + `@packable`のレイアウト制約 | 静的分析を、実行時の構造制約に丸ごと置き換えている |
| API内に並行性を囲い込む | `Parallel.map`のworker pool隠蔽、`SharedBuffer`のフィールド代入の形をとるzero-copy共有 | 「見た目は同期・中身は並列」を、専用の構文でなく既存の代入構文の上に実現 |
| データパラレル向け高レベルAPI | `Parallel.map`（script層） + Tensor（C++ / GPU kernel層） | かなり近い実現。ただし「データはここ」をユーザーに3レーンで明示させる |
| メッセージパッシング（分散の一例として） | Channel（CSP） + Proc | 「分散システムの一例」だったものを、プロセス内の既定の通信手段に格上げ |

通して見ると、一つの型のようなものが貫かれている気がする。ヘルスバーグの発言は
総じて「命令型・共有ヒープの言語はそのままに、コンパイラとAPIをその上に重ねて
安全にする」という前提に立っていた — C#という広く使われる言語を背負う設計者
としては、既存のコードを壊さずに前へ進むための前提だったのだろう。culebraは
公開前の身軽さもあって、各点で、だいたい逆の手を
選んでいる。分析する代わりに共有そのものをなくし、不変性を型に書く代わりに
値を凍結し、ロックを抽象化する代わりにロックが必要になる構造ごと制約してしまう。
これはErlangが1980年代に出した答え（言語の意味論のほうを変えてしまう）の
系譜に近く、彼が「ごく一部の話」と留保しつつ触れたモデルを、むしろ中心に据えた
ような設計になっている。

最後に一つだけ、彼の見立てのほうがculebraより先を行っている部分も、正直に
認めておきたい。「データはここ、演算はこれ」の「ここ」を決めることが、実は
一番むずかしいという点だ。culebraの3レーン — コピー（channel）、凍結参照
（`Shared`）、固定レイアウト（`SharedBuffer`）— は、データの置き場所と性質を
ユーザー自身に申告してもらう仕組みで、彼が思い描いていたような「置き場所を
意識させないAPI」には、まだ届いていない。それを意識させることが、動的型の
言語でdata raceを消すために払う対価なのだ、というのがculebraの設計判断
だけれど、対価なしに済ませた言語はまだない（Rustは型注釈で、Swiftはactor
隔離で、それぞれ別の形の対価を払わせている）という15年あまりを経たいまの
現実こそ、彼の最初の見立て — 魔法のコンパイラスイッチはやって来ない — の
いちばん深いところでの的中なのかもしれない。
