# 循環参照を気にしなくていいRAII

*2026年8月6日*

メモリ管理の設計は、長いあいだ二つの伝統に分かれてきた。

一方はRAIIの伝統である。C++が確立し、Rustが所有権と型システムで
補強した。値の寿命がスコープに紐づき、最後の参照が消えた瞬間に
デストラクタが走る。ファイルは閉じ、ロックは解け、バッファは返る。
「いつ」解放されるかがソースを読むだけで分かるので、リソース管理と
メモリ管理を同じ1つの仕組みに載せられる。代わりに、循環参照は
プログラマの責任として残る — C++の`weak_ptr`、Rustの`Weak`、
SwiftのARCにおける`weak` / `unowned`はどれも、「ここは所有では
ない」と人間が宣言するための道具だ。宣言し忘れれば、そのオブジェクト
は永久にリークする。

もう一方はトレーシングGCの伝統である。Java・Go・C#・JavaScript・
Python（の`gc`モジュール）。到達不能になったものはコレクタがいつか
回収するので、循環参照は最初から問題にならない。代わりに「いつ」が
失われる。finalizerは遅れて走り、順序も不定で、そもそも走る保証が
ない場合すらある（Goの`runtime.SetFinalizer`、Javaが非推奨にした
`finalize`）。だからこれらの言語は、リソース解放をメモリ管理から
切り離した別の仕組み — try-with-resources、`defer`、`using`、
`with`文 — に載せ直すことになる。プログラマは寿命について考えなくて
よくなった代わりに、「メモリ以外の何か」を持つ型については、結局
自分で閉じる場所を書いている。

culebraはこの二つの間に立とうとしている。**リソース管理は必ずRAII、
メモリ管理も可能な限りRAII、しかし循環参照と極端に大きな解放
カスケードだけはGCが引き取る。** 言い換えると、C++やSwiftの決定的な
破棄を持ちながら、`weak`に相当する語を1つも持たない言語である。

このエッセイは、その立ち位置に何の価値があるのか、そしてそれを
成立させるために内部で何をしているのかを書く。実装の詳細は
[`docs/internals/memory.ja.md`](../internals/memory.ja.md)に、観測
可能な契約は[`language.ja.md` §17](../language.ja.md#17-メモリモデル)
にある。ここに書くのは、その二つの間にある「なぜ」のほうだ。

## 書かなくていいもの

まず、ユーザーから見た姿から。引数0個の`drop`プロパティを持つ
オブジェクトは、最後の参照が消えた時点でそれが呼ばれる:

```culebra
{
  r = {drop: fn () {
    inspect('released')
  }}
  inspect('in scope')
}
inspect('after')
# => |
# 'in scope'
# 'released'
# 'after'
```

ここまでは、RCを持つどの言語でも同じことができる。面白いのは
循環を作ったときだ:

```culebra
let closed = []
make_node = fn (name) {
  {name: name, children: [], drop: fn () {
    closed.push(name)
  }}
}
{
  let root = make_node('root')
  let leaf = make_node('leaf')
  root.children.push(leaf)
  leaf.parent = root         # 親への逆参照。ここに weak は要らない
}
inspect(closed)   # => ['leaf', 'root']
```

`leaf.parent`は循環参照である。C++でこれを`shared_ptr`のまま書けば
両者とも永久に解放されず、`drop`は決して走らない。Swiftでも同じで、
親への逆参照は`weak var parent`と書くのが定石になっている。書き忘れた
ときにコンパイラは何も言わない — Instrumentsでリークを見つけて
初めて分かる。

culebraでは、この循環はブロックを抜けた**その場**で解放され、`drop`
も**その場**で走る。GC言語のように「いつか回収される」のではなく、
`}`の位置で決定的に終わる。しかも`closed`の中身が示すとおり、順序も
子から親へと入れ子の内側から解けていく。

同じ性質はリソースの側から見るともっと重要になる。ファイル
ディスクリプタ・ソケット・DB接続・ロック・GPUバッファは、メモリと
違って希少で、解放が数百ミリ秒遅れるだけで観測可能な障害になる。
culebraのstdlibはこれらをすべて`drop`の上に載せている:

```culebra
# doctest: skip
# 1. スコープ付きヘルパー: 正常・return・throw のどの経路でも閉じる
let head = File.with('big.log', 'r', fn (f) { f.read(256) })

# 2. 寿命がブロックより広いとき
let f = File.open(path, 'w')
defer { f.close() }

# 3. iterator がハンドルを所有する。break で抜けても閉じる
for line in File.open(path).lines() {
  if line == '' { break }
  process(line)
}
```

3番目が言いたいことを一番よく表している。`File.open(path).lines()`は
どの変数にも束縛されていない。それでもループを`break`で抜けた時点で
ハンドルは閉じる — 例外で抜けても同じだ。これがGC言語なら、この形は
「fdがいつ閉じるか分からないので書いてはいけない形」になる。

つまりculebraのユーザーが書かないものは、`weak`と`unowned`、
`Rc<RefCell<...>>`のような所有権の器、`GC.collect()`の手動呼び出し、
そして「メモリはGCが見るがファイルは自分で閉じる」という二重帳簿
である。

## なぜ`weak`を入れなかったか

`weak`を導入するのは、実装としてはむしろ簡単な道だった。入れなかった
のは、それが**正しさの責任をユーザーへ移す**道具だからだ。

循環参照は、書こうとして書くものではない。親を指し返すツリー、
observerが被観測者を覚えているグラフ、キャッシュ、双方向リンク、
自分自身を呼ぶために自分を捕捉した再帰クロージャ。どれも設計として
自然で、循環はその副産物として現れる。静的型と借用検査を持つ言語なら
「ここは所有ではない」を型に書かせるのは筋が通る。だが動的型で、
スクリプトのように書き下す言語で同じことを要求すると、実際に起きるのは
「循環しているかどうかを人間が探す作業」が増えることであって、
リークが減ることではない。Swift ARCという、配置をすべてコンパイラが
生成する（プログラマの誤りが入る余地がない）ほど徹底した実装ですら、
retain cycleは日常的にリークしている。RCの規律をどれだけ厳しくしても
この穴は塞がらない、というのは実証済みだと考えていい。

そこでculebraは逆にした。循環は**言語が引き取る**。ユーザーは所有の
形を宣言しないし、`drop`が走らなくなる書き方を心配しなくてよい。
その代わり、循環の回収だけはRCの外側にある機構 — トレーシング
コレクタ — に委ねる。

ここで大事なのは主従関係である。**RCが「いつ」を決め、tracingは
「RCにできないこと」だけを引き受ける。** 逆にはしない。純粋な
tracingへ寄せる（手書きRCを全廃する）案も検討したが、それは決定的な
`drop`を諦めることであり、上に書いた性質 — `}`でファイルが閉じる —
が丸ごと失われる。共有所有の下で決定的なfinalizationを与えられる
のは厳密な参照カウントだけで、カウントが0になること自体がシグナル
であり、それは最後の参照が解放された瞬間に起きる。GCは、その瞬間を
観測する道具を持っていない。

## 実装: 2つのエンジン、1つの契約

culebraにはbackendが2つあり（インタプリタとJIT、AOTはJITと同じ
コード生成を使う）、どちらも「RC主体 + tracingバックストップ」という
同じ構造をしている。同じプログラムが同じタイミングで同じ`drop`を
起こさなければならないので、これは選択の余地がなかった。だが、
2つのエンジンが抱えている**難しさ**は完全に別物だった。

### インタプリタ: 難しさがそもそも存在しない側

インタプリタはヒープ値をC++の`shared_ptr`として表現する。したがって
参照カウントは**構築によって**厳密である。increment/decrementを
書くのは人間ではなくコンパイラで、`shared_ptr`のデストラクタは
`break`でも早期`return`でも例外unwindでも素通りされない。RC配置に
起因するリークと二重解放は、この側では起こりうるバグの種類に入って
いない。

残る露出は循環だけなので、コレクタもそれ専用でよい。インタプリタの
コレクタはCPythonと同じアルゴリズムを使う: 追跡対象の各オブジェクト
について、他の追跡対象が保持している参照の数（ヒープ内エッジ）を
refcountから差し引き、残りが0なら追跡集合の外から誰も指していない
— すなわちガベージサイクルだと判定する。`shared_ptr`のカウントが
厳密だからこそ成り立つ**精密**なコレクタで、C++スタックを覗く必要が
ない。

面白いのは、その精密さを支えているのが解析ではなく**スケジュール**
だという点だ。collectionは任意の時点では走らず、次の**文境界**まで
遅延される。生成されたばかりの自己参照クロージャがC++の戻り値として
関数の間を通過中で、まだどの環境からも到達できない — という危うい
瞬間は確かに存在するが、次の文境界に達するころにはその値は必ず
どこかの環境へ格納されている。「危険な窓の中では絶対に走らない」と
決めることで、保守的なスタックスキャンが丸ごと不要になっている。

### JIT: `shared_ptr`のない世界

JITは値ごとに、retainとreleaseを明示的なLLVM IRとして発行する。値に
触れるたびにアトミックなrefcount操作が走る`shared_ptr`のコストを
避けるためだが、この選択は、インタプリタ側には存在しなかった問題を
そっくり呼び戻す。生成するあらゆるコードパスで、retainとreleaseの
配置を自分で正しく行わなければならず、パスを1つ見落としたときに
助けてくれるデストラクタは存在しない。失敗の形はちょうど2つ:
**解放漏れ**（リーク）と**過剰な解放**（use-after-free）。しかも
fall-through・`break`・`continue`・早期`return`・複数スコープを
またぐ例外unwindの全てが、そのコードパスに数えられる。

これを1件ずつ見つけて直す方針は、やってみると収束しない。1つ直す
たびに、まだ監査していない次のパスが同じ間違いに対して無防備なまま
残るからだ。そこで方針を変えた: **正しく配置されたretain/releaseが、
新しいcodegenを書く唯一の方法になるようにする。**

### 生成コードの上にRAIIを重ねる

このとき使った道具が、culebraがユーザーへ提供しているものと同じ
RAIIだった、というのがこの設計のいちばん気に入っている点だ。
LLVM IRを吐くC++のコードに、C++のデストラクタで組んだ所有権の層を
重ねる。層は下から順に、リークまたは二重解放が起きる経路を1つずつ
塞いでいく:

- **一貫した規約。** 式をコンパイルする関数はすべて、呼び出し側が
  参照を1つ所有する値（`+1`値）を返す。パラメータとreceiverは
  *借用*（`+0`）される。retain/releaseの位置を1箇所ずつ判断するの
  ではなく、1つの規約から**導出する** — Swift ARCから借りた発想だ。
- **move-onlyハンドル。** `+1`値は裸のポインタではなくmove-onlyの
  RAIIハンドルに入る。ハンドルは「読む」「ちょうど1回次へ手渡す」
  「その場で解放する」しか提供しない。使用済みのハンドルをもう一度
  消費することは**コンパイル時abort**である — 二重解放がビルド失敗に
  変換される。渡されないまま死ねばデストラクタが解放する。
- **直線領域を脱出する値はスコープスロットが所有する。** ループ反復を
  またぐ値や、片方の分岐で消費され他方で捨てられる値は、スコープ
  スロットへ移す。既存のスコープ巻き戻しが、通常のfall-through・
  `break` / `continue`・早期`return`・例外unwindという*あらゆる*
  脱出経路でそれを解放する。これは実際に出荷されていたリークを
  1クラス塞いだ — 以前はスコープが所有するローカル変数の`drop`が、
  `throw`で抜けたときだけ一度も走っていなかった。
- **借用値には解放操作が存在しない。** 借用ハンドルの型に
  releaseメソッドが無いので、「借りたものを解放してしまった」という
  バグは表現不能である。
- **裸の参照は、生成されたbasic blockの中に閉じ込める。** 最後に
  残っていた抜け道は、ハンドルから値を読み出した瞬間だった。今は
  読み出しが生成元のblockを記録したトークンを返し、それを別のblockで
  使うとコンパイル時abortになる。throwしうる呼び出しはすべて`invoke`
  としてコンパイルされ、`invoke`は必ず自分のblockを終端するので、
  「まだ同じblockにいる」は「その参照が生まれてから例外unwindの縁を
  一度も越えていない」と同義になる — この規則が健全かつ完全である
  理由がこれで、実際、最近見つかったリークはすべてこの形をしていた。

積み上がると、リークや二重解放を起こすには**C++の型かRAII不変条件
のどれかを破らなければならなく**なる。それは実行時の事故ではなく、
コンパイルエラーとして出る。ランタイムhelperをまたいで所有権が移る
数少ない場所には閉じた契約の集合（呼び出し側が掃除する／helperが
throw時に掃除する／helperが常に消費する／参照カウント中立／そのまま
転送する）があり、同じ値に2つのcleanerが割り当てられることは構造上
起きない — それはそのまま二重解放になるからだ。

whole-functionのIRベリファイアを書く案もあったが、これは検討の上で
却下している。C++ helperの内部を見られないうえ、「すべてのretainに
releaseが対応している」は「すべての値がちょうど必要な期間だけ生きて
いた」を意味しない。早いが釣り合った解放は、生きているuse-after-free
の窓を残す。上のblock閉じ込め規則が意図的にもっと狭いスコープしか
持たない — この規律自身のハンドルについてしか推論しない — ことが、
ベリファイア案を沈めた異論を回避できている理由でもある。

### バックストップ: 保守的で、動かないコレクタ

規律をどれだけ積んでも循環は解けない。これは構築上の限界で（Rustの
`Rc`も同じ制約を持つ）、いかなるRC規律も単独では超えられない。
だからJIT側にもトレーシングコレクタがある。役割はインタプリタの
コレクタと正確に同じ — 両backendが同じ循環形状を回収することが、
振る舞いの対称性の一部になっている — が、機構は正反対だ。JITの
手書きRCには`shared_ptr`のような厳密さがないので、精密なコレクタは
成立しない。代わりに**保守的**にroot探索する。

collectionの瞬間、全mutatorスレッドのマシンスタックとcallee-saved
registerを8バイト単位で一様に走査し、有効なオブジェクトの開始
アドレスに着地するワードをすべてrootとして扱う。タグは見ない —
タグ付き整数の中に隠れたヒープポインタも、タグの中身に関係なく
見つかる。これが健全なのは、呼び出し規約の帰結として、collectionを
起こしうる呼び出しをまたいで生きているポインタは必ずスタックへ
spillされているかcallee-saved registerに入っているからで、Boehmや
Rubyの保守的コレクタを支えているのと同じ論拠である。実際にデバッグ
時間を要した細部が1つあって、探索はframe pointerではなく**stack
pointer**から始めなければならない。`-O2`以上ではframe pointerより
下にあるspillを取りこぼす。

たまたま有効なヒープアドレスに一致した整数は**偽のroot**を作り、
死んでいるオブジェクトを生かしてしまう。これは有界な過剰保持で
あって、正当性の問題ではない — 健全性が要求するのは「生きている
ものが解放されないこと」だけだ。

コレクタは何も**移動させない**。これは延期ではなく確定した決定で、
理由は2つある。保守的なrootは定義上「ポインタかもしれないワード」
なので、移動後の新しい位置に書き換えられない。そしてculebraは
Tensorやインタプリタとの相互運用のためにC++へ生ポインタを渡して
おり、値表現がタグ付き64bit整数であることも相まって、JITのrootを
精密にする標準的な方法（LLVM Statepoints）が使えない。CPython・
Lua・Rubyの既定コレクタがどれもnon-movingであるのと、同じ理由が
並んでいる。movingが唯一もたらす利点 — compactionと、ヒープ
サイズではなく生存者数に比例するcollectionコスト — は、いまの
culebraにとっては二次的な関心事だと判断した。

死んだオブジェクトの`drop`は、メモリを回収する前、構造がまだ無傷の
うちに走る。これはCPythonがPEP 442で選んだのと同じ精神で、
finalizerが半壊したオブジェクトグラフを観測しないことを保証する。

コレクタ自身のC++実装も、生成コードに課しているのと同じ規律に
従っている: teardownは普通の構造体のデストラクタ、stop-the-worldの
調整はスコープガード、global rootの登録はスコープの寿命に紐づく。
手で対にしたsetup/teardownの呼び出しは、この実装のどこにも無い。

## GCがあると、RCのバグが静かになる

「RC + GCバックストップ」には、あまり語られない副作用がある。
**RC配置のバグが症状を出さなくなる。** retainを1つ余分に置いて
しまっても、そのオブジェクトはリークしたまま到達不能になり、次の
collectionが黙って回収する。プログラムは正しく動き、テストは緑で、
メモリ使用量がじわじわ増えることだけが、はるか後になって唯一の
手掛かりとして残る。バックストップは安全網であると同時に、
証拠隠滅の装置でもある。

そこで、これを検出する仕掛けを別に用意した。上に書いた2つの
コレクタは、同じヒープに対して**独立した2つの意見**を出せる —
精密な参照会計（refcountからヒープ内エッジを差し引く）と、保守的な
スタックスキャンだ。2つが食い違うオブジェクトを見ると、正確な
診断になる:

- 保守的スキャンでは死んでいて、参照会計では生きていて、しかし他の
  追跡対象からも到達できない → そのオブジェクトのrefcountは、実際に
  それを指している参照の数より多い。これは**確定的なRC配置バグ**で、
  無害な説明があり得ない。
- 保守的スキャンでは死んでいて、参照会計では生きていて、他の追跡対象
  からは到達できる → ただの循環参照。想定内であり、バックストップが
  存在する理由そのもの。

前者は**偽陽性がゼロ**である。通常のプログラム構造からは決して生じ
ないので、1件出れば必ずバグだ。この分類器の上に、debugビルド・CI
専用のリーク検出器が乗っている: 全オブジェクトの生成時backtraceを
記録し、慎重に選んだ1つの静止点 — トップレベルの実行が終わり、
moduleとnamespaceのrootはまだ配線されている瞬間。「refcountが過剰で
他は死んでいる」が「まだ到達可能と観測されていないだけ」ではなく
確実に「リークしている」を意味する、唯一の地点 — で分類器を走らせ、
見つかれば生成箇所を添えてabortする。これがコンフォーマンステスト
全体（例外throw経路を含む）に対して、CIの常設フェーズとして回って
いる。出荷ビルドではabortしない。abort自体がサービス拒否の
ベクタになりうるからで、そちらは静かに回収を続ける。

もう1つ、診断用のトグルがすべてのcollectionを無効化する。この状態で
**残る**クラッシュはルーティングの問題ではありえない（何も回収されて
いない）ので、純粋な所有権のバグ — 生きている値が解放された — だと
分かる。**消える**クラッシュは逆にrootの取りこぼしだったことになる。
実際にはこの方法で調べたクラッシュはこれまで全て前者で、両コレクタの
root探索が実バグの原因になったことは、出荷以来1度もない。

コレクタ側にはストレスモードもある。適応的なスケジュールの代わりに
**すべてのアロケーションで**collectするので、タイミング依存で
気まぐれに現れるバグが決定論的に表面化する（SpiderMonkeyの`gcZeal`と
同じ発想）。フルなコンフォーマンススイートはこのモードでも緑で走る。

## 払っている代償

この立ち位置は無料ではない。正直に並べておく。

**トップレベル束縛は`drop`されない。** `drop`を持つオブジェクトを
トップレベルに束縛すると、どのbackendでもプログラム終了まで生き残り、
`drop`は走らない。インタプリタのトップレベル環境は、そこに束縛された
関数群が自分自身を捕捉する巨大な循環なので破棄されず、JIT / AOTは
振る舞いを揃えるために意図的に抑制している。スクリプト全体にわたる
リソースには`defer`か明示的なクリーンアップを使うことになる。

**極端に大きな循環は遅れる。** スコープ離脱のカスケードには、通常の
プログラムを同期的に保つためのサイズ上限がある。1つのスコープが
数千単位の循環所有オブジェクトを一度に手放すと、超過分はGC
バックストップへ委ねられ、finalize順序も未規定になる。失われはせず
遅れるだけだが、決定性が保証されるのは「通常の規模まで」だという
但し書きが付く。

**保守的スキャンの過剰保持。** 偽rootは有界とはいえ実在する。
生きているものが誤って解放されることはないが、死んだものが1
collection余分に居座ることはある。

**movingコレクタを永久に諦めている。** 断片化が実測で問題になるか、
生ポインタの相互運用をハンドルかpinningの背後に再設計しない限り、
この決定は動かない。

そして最後に、いちばん大きなもの: **処理系側のコード量と複雑さが
大きい**（実行速度の話ではなく、作り込みの話である）。GCだけの言語
ならコレクタ1つで済み、RCだけの言語ならユーザーに`weak`を書かせれば
済む。culebraは両方を持ち、しかも機構が正反対な2つのbackendで
振る舞いを一致させ、さらに「RCのバグをGCが隠す」問題を埋めるための
検出器まで持っている。ユーザーが書かなくてよくなった`weak`の1語は、処理系の
側にこれだけの構造として現れている。それでも割に合っていると考えて
いるのは、`weak`の書き忘れがユーザーのプログラムで起こす失敗は
静かで再現しにくいのに対し、処理系側の複雑さは1箇所に集約でき、
CIで毎日検査できるからだ。

## 系譜

この設計はどれか1つのシステムを丸ごと採ったものではない。各所から
1つずつ構造的なアイデアを借りている。

| 出どころ | 借りたもの |
|---|---|
| C++ RAII | 実装の乗り物そのもの。デストラクタが解放を発行するハンドルは、早期returnや例外をまたいでも自動的に正しい |
| Rust（affine ownership、`Drop`） | move-or-consumeを値の基本規律にすること。借用は分類上決して解放されない |
| Swift ARC | retain/release配置を1箇所ずつ判断せず、1つの一貫した規約から*導出する*という発想 |
| CPython | 精密なサイクル検出（`gc_refs`減算）と、finalizeをsweep前に行うPEP 442の順序 |
| Nim（ORC）・Perceus（Koka） | 「RC主体 + サイクル回収backstop」が理論上の妥協ではなく出荷可能な組み合わせだという裏付け |
| Boehm GC・Ruby | 保守的なスタックスキャンが最適化コンパイラの下でも健全である論拠 |
| SpiderMonkey（`gcZeal`） | アロケーションごとにcollectして、タイミング依存のバグを決定論に変えるストレスモード |
| MLIR / Swift SIL ownership | 目指している到達点。所有権が、レビュアーが目視で守るコメント上の約束ではなく、中間表現がチェックできる性質であること |

## まとめ

culebraのメモリ管理は、「RAIIとGCのどちらが正しいか」という問いに
答えを出していない。**リソースにはRAIIが要る。循環にはGCが要る。
だから両方積む** という、答えを回避する形の設計になっている。RCが
「いつ死ぬか」を決めて`drop`のタイミングを駆動し、tracingは
「RCが構造上扱えないもの」だけを回収する。ユーザーから見えるのは、
`}`でファイルが閉じることと、親を指し返しても何も起きないことの
2つだけだ。

その裏側で処理系がやっていることを一言でまとめるなら、**ユーザーに
渡しているRAIIを、処理系自身の実装でも使っている**、という入れ子に
なる。JITのコード生成はC++のRAIIハンドルでretain/releaseを組み立て、
コレクタのteardownは普通のデストラクタで、stop-the-worldはスコープ
ガードで、リーク検出器は2つのコレクタに独立な意見を出させて突き
合わせる。設計として一貫しているかどうかは、たぶんこの入れ子が
どこまで保てるかで決まる。
