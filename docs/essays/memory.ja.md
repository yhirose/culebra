# 循環参照を気にしなくていいRAII

*2026年8月6日（2026年9月1日改訂）*

メモリ管理の設計は、長いあいだ二つの伝統に分かれてきた。

一方はRAIIの伝統である。C++が確立し、Rustが所有権と型システムで
補強した。値の寿命がスコープに紐づき、最後の参照が消えた瞬間に
デストラクタが走る。ファイルは閉じ、ロックは解け、バッファは返る。
「いつ」解放されるかがソースを読むだけで分かるので、リソース管理と
メモリ管理を同じ1つの仕組みに載せられる。代わりに、循環参照は
プログラマの責任として残る — C++の`weak_ptr`、Rustの`Weak`、
SwiftのARCにおける`weak` / `unowned`はどれも、「ここは所有では
ない」と人間が宣言するための道具だ。宣言し忘れれば、そのオブジェクト
は永久にリークする。

もう一方はトレーシングGCの伝統である。Java・Go・C#・JavaScript。
到達不能になったものはコレクタがいつか回収するので、循環参照は
最初から問題にならない。代わりに「いつ」が失われる。finalizerは
遅れて走り、順序も不定で、そもそも走る保証がない場合すらある（Goの`runtime.SetFinalizer`、Javaが非推奨にした
`finalize`）。だからこれらの言語は、リソース解放をメモリ管理から
切り離した別の仕組み — try-with-resources、`defer`、`using`、
`with`文 — に載せ直すことになる。プログラマは寿命について考えなくて
よくなった代わりに、「メモリ以外の何か」を持つ型については、結局
自分で閉じる場所を書いている。

culebraはこの二つの間に立とうとしている。**リソース管理はRAIIを
既定とし、メモリ管理も可能な限りRAII、循環参照といくつかの縁の
ケースだけをGCが引き取る。** 言い換えると、C++やSwiftの決定的な
破棄を持ちながら、`weak`に相当する語を1つも持たない言語である。
GCへ回る縁のケース（トップレベル束縛、クロージャだけが作る循環、
極端に大きな解放カスケード）は「払っている代償」節でまとめて挙げる。

このエッセイは、その立ち位置に何の価値があるのか、そしてそれを
成立させるために内部で何をしているのかを書く。実装の詳細は
[`docs/internals/memory.ja.md`](../internals/memory.ja.md)に、観測
可能な契約は[`language.ja.md` §17](../language.ja.md#17-メモリモデル)
にある。食い違いがあれば`language.ja.md`が勝つ。

## 書かなくていいもの

まず、ユーザーから見た姿から。引数0個の`drop`プロパティを持つ
オブジェクトは、最後の参照が消えた時点でそれが呼ばれる:

```culebra
{
  r = {drop: fn () {
    inspect('released')
  }}
  inspect('in scope')
}
inspect('after')
# => |
# 'in scope'
# 'released'
# 'after'
```

ここまでは、RCを持つどの言語でも同じことができる。面白いのは
循環を作ったときだ:

```culebra
let closed = []
make_node = fn (name) {
  {name: name, children: [], drop: fn () {
    closed.push(name)
  }}
}
{
  let root = make_node('root')
  let leaf = make_node('leaf')
  root.children.push(leaf)
  leaf.parent = root  # 親への逆参照。ここに weak は要らない
}
inspect(closed)  # => ['leaf', 'root']
```

`leaf.parent`は循環参照である。素の`shared_ptr`のまま、あるいは
Swiftで`weak var parent`と書かずに同じ形を作れば、両者とも永久に
解放されず、`drop`は決して走らない。

culebraでは、この循環はブロックを抜けた`}`の位置で解放され、`drop`
もそこで走る。GC言語のように「いつか回収される」のではなく、決定的に
終わる。順序は循環メンバーを**新しく束縛されたものから**で、`leaf`が
先に閉じるのはそれが後から作られたからだ（循環でない通常のカスケード
は逆に親→子で、正確な規定は§17にある）。

同じ性質はリソースの側から見るともっと重要になる。ファイル
ディスクリプタやDB接続は、メモリと違って希少で、解放が数百ミリ秒
遅れるだけで観測可能な障害になる。culebraのstdlibはこれらを`drop`の
上に載せていて、明示的に閉じられなかったハンドルだけがGCバック
ストップに回る:

```culebra
# doctest: skip
# 1. スコープ付きヘルパー: 正常・return・throw のどの経路でも閉じる
let head = File.with('big.log', 'r', fn (f) {
  f.read(256)
})

# 2. 寿命がブロックより広いとき
let f = File.open(path, 'w')
defer {
  f.close()
}

# 3. iterator がハンドルを所有する。break で抜けても閉じる
for line in File.open(path).lines() {
  if line == '' {
    break
  }
  process(line)
}
```

3番目が言いたいことを一番よく表している。`File.open(path).lines()`は
どの変数にも束縛されていない。それでもループを`break`で抜けた時点で
ハンドルは閉じる — 例外で抜けても同じだ。これがGC言語なら、この形は
「fdがいつ閉じるか分からないので書いてはいけない形」になる。

つまりculebraのユーザーが書かないものは、`weak`と`unowned`、
`Rc<RefCell<...>>`のような所有権の器、そして「メモリはGCが見るが
ファイルは自分で閉じる」という二重帳簿である。

## なぜ`weak`を入れなかったか

`weak`を導入するのは、実装としてはむしろ簡単な道だった。入れなかった
のは、それが**正しさの責任をユーザーへ移す**道具だからだ。

循環参照は、書こうとして書くものではない。親を指し返すツリー、
observerが被観測者を覚えているグラフ、キャッシュ、双方向リンク、
自分自身を呼ぶために自分を捕捉した再帰クロージャ。どれも設計として
自然で、循環はその副産物として現れる。静的型と借用検査を持つ言語なら
「ここは所有ではない」を型に書かせるのは筋が通る。だが動的型で、
スクリプトのように書き下す言語で同じことを要求すると、実際に起きるのは
「循環しているかどうかを人間が探す作業」が増えることであって、
リークが減ることではない。retain/releaseの配置をすべてコンパイラが
生成するSwift ARC — 配置に関してはプログラマの誤りが入る余地がない
実装 — でも、循環だけは`weak` / `unowned`という宣言に委ねる設計を
採っており、実際に残るリークもそこに集中する。RCの規律をどれだけ
厳しくしても循環は自力で解けない、という構造的な限界がここに見える。

そこでculebraは逆にした。循環は**言語が引き取る**。ユーザーは所有の
形を宣言しないし、`drop`が走らなくなる書き方を心配しなくてよい。
その代わり、循環の回収だけはRCの外側にある機構 — トレーシング
コレクタ — に委ねる。

ここで大事なのは主従関係である。**RCが「いつ」を決め、tracingは
「RCにできないこと」だけを引き受ける。** 逆にはしない。純粋な
tracingへ寄せる（手書きRCを全廃する）案も検討したが、それは決定的な
`drop`を諦めることであり、上に書いた性質 — `}`でファイルが閉じる —
が丸ごと失われる。共有所有の下で決定的なfinalizationを与えられる
のは厳密な参照カウントだけで、カウントが0になること自体がシグナル
であり、それは最後の参照が解放された瞬間に起きる。GCは、その瞬間を
観測する道具を持っていない。

## 実装: retain/releaseを置くのは1度だけ

culebraがプログラムを動かす道は2つある。既定であるバイトコードVMの
executorと、`--jit`と`culebra build`が使うLLVM loweringである。ただし
これは、言語の実装が2つあるという意味ではない。プログラムを
バイトコードに変えるコンパイラは1つで、retainとreleaseはその
バイトコードの中の命令になっている。だから2つのレーンがそれぞれ配置を
決めるのではなく、1つの配置をそのまま実行する。同じプログラムは両方で
同じ位置で同じ`drop`を起こす。決まったタイミングで解放されない形 —
クロージャだけで閉じた循環、大きすぎる解放の連鎖、トップレベルの束縛
— も両方で同じで、§17に挙げてある。

ずっとこうだったわけではない。この先に書く規律は、前の設計には無かった
問題への答えなので、何が変わったのかを先に書いておく。2026年まで、
既定のエンジンはヒープ上の値をC++の`shared_ptr`として持つ
tree-walkingインタプリタだった。参照カウントは**作りからして**厳密
だった。増減を書くのは人間ではなくコンパイラで、`shared_ptr`の
デストラクタは`break`でも早期`return`でも例外のunwindでも飛ばされない。
RCの配置を間違えて起こるリークや二重解放は、この側では起こりようが
なかった。残る危険は循環参照だけなので、コレクタもそれ専用でよく、
**精密**にできた。C++のスタックを見る必要がなかったのは、collectionを
次の文の切れ目まで遅らせていたからである。作ったばかりの自己参照
クロージャがC++の関数から関数へ渡されている途中で、まだどの環境からも
たどれない、という危ない瞬間はあるが、次の文の切れ目まで待てばその値は
必ずどこかに格納されている。

そのエンジンはもう無い。1つの言語に実装を2つ持つのは、そこから得られる
確認の価値より、2つをずれないように保つ手間のほうが大きかった。残った
のは、コンパイルするレーンとフロントエンドを共有する側である。ただ、
インタプリタより長生きしたものがある。仕掛けではなく、アルゴリズムの
ほうだ。同じ精密な参照計算は、いまも1つになったヒープの上で動いている。
コレクタとしてではなく、バグを見つける道具として。これは下の「GCがある
と、RCのバグが静かになる」で扱う。

### `shared_ptr`のない世界

retainとreleaseは、いまはどこでも明示的な操作で、よく通る経路に
`shared_ptr`は1つもない。値に触れるたびにアトミックな参照カウント操作が
走るコストは避けられるが、代わりに、インタプリタ側には無かった問題が
そのまま戻ってくる。どのコードパスでも、retainとreleaseを自分で正しく
置かなければならず、1つ見落としたときに助けてくれるデストラクタはない。
失敗の形はちょうど2つ、**解放し忘れ**（リーク）と**解放しすぎ**
（use-after-free）である。しかも、そのまま次へ進む場合・`break`・
`continue`・早期`return`・複数のスコープをまたぐ例外のunwindが、すべて
別々のコードパスとして数えられる。

これを書く場所は3つあって、1つ目がいちばん楽だ。バイトコード
コンパイラは、retainとreleaseを1か所で1度だけ出す。2つのレーンはそれを
実行するだけなので、この配置は1度検証すれば両方に効く。残る2つは
難しい。バイトコードの命令を1つloweringすると、複数の値が同時に宙に
浮くことがある。別の呼び出しをまたいで保持するヘルパーの戻り値や、
メソッドの実行中だけ借りているレシーバなどだ。これを決めるのはIRを
組み立てるC++のほうで、さらに、loweringした呼び出しが飛び込む先の
ランタイムヘルパーも、自分の分を自分で置く。

これを1件ずつ見つけて直す方針は、やってみると収束しない。1つ直す
たびに、まだ監査していない次のパスが同じ間違いに対して無防備なまま
残るからだ。そこで方針を変えた: **正しく配置されたretain/releaseが、
新しいcodegenを書く唯一の方法になるようにする。**

### 生成コードの上にRAIIを重ねる

このとき使った道具が、culebraがユーザーへ提供しているものと同じ
RAIIだった、というのがこの設計のいちばん気に入っている点だ。
LLVM IRを吐くC++のコードに、C++のデストラクタで組んだ所有権の層を
重ねる。層はそれぞれ、リークまたは二重解放が起きる経路を1つずつ
塞いでいく。主なものを挙げると（全体はinternals §4.3）:

- **一貫した規約。** 式をコンパイルする関数はすべて、呼び出し側が
  参照を1つ所有する値（`+1`値）を返す。パラメータとreceiverは
  *借用*（`+0`）される。retain/releaseの位置を1箇所ずつ判断するの
  ではなく、1つの規約から**導出する** — Swift ARCから借りた発想だ。
- **move-onlyハンドル。** `+1`値は裸のポインタではなくmove-onlyの
  RAIIハンドルに入る。ハンドルは「読む」「ちょうど1回次へ手渡す」
  「その場で解放する」しか提供しない。使用済みのハンドルをもう一度
  消費することは**コンパイル時abort**である — 二重解放がビルド失敗に
  変換される。渡されないまま死ねばデストラクタが解放する。
- **直線領域を脱出する値はスコープスロットが所有する。** ループ反復を
  またぐ値や、片方の分岐で消費され他方で捨てられる値は、スコープ
  スロットへ移す。既存のスコープ巻き戻しが、通常のfall-through・
  `break` / `continue`・早期`return`・例外unwindという*あらゆる*
  脱出経路でそれを解放する。これは実際に出荷されていたリークを
  1クラス塞いだ — 以前はスコープが所有するローカル変数の`drop`が、
  `throw`で抜けたときだけ一度も走っていなかった。
- **借用値には解放操作が存在しない。** 借用ハンドルの型に
  releaseメソッドが無いので、「借りたものを解放してしまった」という
  バグは表現不能である。
- **裸の参照は、生成されたbasic blockの中に閉じ込める。** 最後に
  残っていた抜け道は、ハンドルから値を読み出した瞬間だった。今は
  読み出しが生成元のblockを記録したトークンを返し、それを別のblockで
  使うとコンパイル時abortになる。throwしうる呼び出しはすべて`invoke`
  としてコンパイルされ、`invoke`は必ず自分のblockを終端するので、
  「まだ同じblockにいる」は「その参照が生まれてから例外unwindの縁を
  一度も越えていない」と同義になる — この規則が健全かつ完全である
  理由がこれで、実際、最近見つかったリークはすべてこの形をしていた。
  本当にblockをまたぐ少数の形には明示的にuncheckedな変種があるが、
  そのサイト数は数えられていて、増やすことは許されていない。

積み上がると、リークや二重解放を起こすには**C++の型かRAII不変条件
のどれかを破らなければならなく**なる。それは実行時の事故ではなく、
コンパイルエラーとして出る。ランタイムhelperをまたいで所有権が移る
数少ない場所には閉じた契約の集合があり、同じ値に2つのcleanerが
割り当てられることは構造上起きない — それはそのまま二重解放になる
からだ。

whole-functionのIRベリファイアを書く案もあったが、これは検討の上で
却下している。C++ helperの内部を見られないうえ、「すべてのretainに
releaseが対応している」は「すべての値がちょうど必要な期間だけ生きて
いた」を意味しない。早いが釣り合った解放は、生きているuse-after-free
の窓を残す。上のblock閉じ込め規則が意図的にもっと狭いスコープしか
持たない — この規律自身のハンドルについてしか推論しない — ことが、
ベリファイア案を沈めた異論を回避できている理由でもある。

### バックストップ: 保守的で、動かないコレクタ

規律をどれだけ積んでも循環は解けない — Rustの`Rc`も共有する、構築上
の限界である。だからランタイムにもトレーシングコレクタがある。ただし
その仕組みは、退役したインタプリタのものとは正反対だ。手で置くRCには
`shared_ptr`のような厳密さがないので、精密なコレクタは成立しない。
代わりに**保守的**にrootを探す。

collectionの瞬間、全mutatorスレッドのマシンスタックとcallee-saved
registerを8バイト単位で一様に走査し、有効なオブジェクトの開始
アドレスに着地するワードをすべてrootとして扱う。タグは見ない —
タグ付き整数の中に隠れたヒープポインタも、タグの中身に関係なく
見つかる。これが健全なのは、呼び出し規約の帰結として、collectionを
起こしうる呼び出しをまたいで生きているポインタは必ずスタックへ
spillされているかcallee-saved registerに入っているからで、Boehmや
Rubyの保守的コレクタを支えているのと同じ論拠である（走査の詳細と
グローバルroot集合はinternals §6.2）。

ただしこれは機械の性質に頼った話なので、culebraが配布している環境の
1つでは成り立たない。wasmでは、関数が扱っている値はlocalに入る。
localは線形メモリの外にあり、そこへ書き出す仕組みもないので、走査から
はまったく見えない。この問題は走査の側では直せないので、collectionを
**いつ**行うかのほうを変えて解決した。wasmでは、メモリを確保した時点
ではcollectionしない。閾値を越えたら印をつけておくだけにして、
executorが命令の切れ目でそれを見に行く。その時点なら、どのフレームの
生きている値も、走査から見えるレジスタの配列に入っている
（internals §6.5）。退役したインタプリタが採ったのと同じ手である。
rootを見えるようにできないなら、すでに見えている瞬間にだけ回収する。

たまたま有効なヒープアドレスに一致した整数は**偽のroot**を作り、
死んでいるオブジェクトを生かしてしまう。これは有界な過剰保持で
あって、正当性の問題ではない — 健全性が要求するのは「生きている
ものが解放されないこと」だけだ。

コレクタは何も**移動させない**。これは延期ではなく確定した決定で、
理由は2つある。保守的なrootは定義上「ポインタかもしれないワード」
なので、移動後の新しい位置に書き換えられない。そしてculebraは
Tensorやホストとの相互運用のためにC++へ生ポインタを渡して
おり、値表現がタグ付き64bit整数であることも相まって、JITのrootを
精密にする標準的な方法（LLVM Statepoints）が使えない。後者 — 協調
しないCコードへ生ポインタが出ていくこと — は、CPython・Lua・Rubyの
既定コレクタがどれもnon-movingである理由でもある。movingが唯一
もたらす利点 — compactionと、ヒープ
サイズではなく生存者数に比例するcollectionコスト — は、いまの
culebraにとっては二次的な関心事だと判断した。

死んだオブジェクトの`drop`は、メモリを回収する前、構造がまだ無傷の
うちに走る。これはCPythonがPEP 442で選んだのと同じ精神で、
finalizerが半壊したオブジェクトグラフを観測しないことを保証する。

コレクタ自身のC++実装も、生成コードに課しているのと同じ規律に
従っている: teardownは普通の構造体のデストラクタ、stop-the-worldの
調整はスコープガード、global rootの登録はスコープの寿命に紐づく。
手で対にしたsetup/teardownの呼び出しは、この実装のどこにも無い。

## GCがあると、RCのバグが静かになる

「RC + GCバックストップ」には、あまり語られない副作用がある。
**RC配置のバグが症状を出さなくなる。** retainを1つ余分に置いて
しまっても、そのオブジェクトはリークしたまま到達不能になり、次の
collectionが黙って回収する。プログラムは正しく動き、テストは緑で、
メモリ使用量がじわじわ増えることだけが、はるか後になって唯一の
手掛かりとして残る。バックストップは安全網であると同時に、
証拠隠滅の装置でもある。

そこで、これを見つける仕掛けを別に用意した。ヒープ上のオブジェクトが
生きているかどうかを判定する方法は2つある。1つは精密な参照計算で、
CPythonと同じく、refcountからヒープ内の参照の数を差し引く。これを
診断目的でそのヒープに対して走らせる。もう1つは、コレクタ自身の保守的な
スタックスキャンである。この**独立した2つの
意見**が食い違うオブジェクトを見ると、正確な診断になる:

- 保守的スキャンでは死んでいて、参照会計では生きていて、しかし他の
  追跡対象からも到達できない → そのオブジェクトのrefcountは、実際に
  それを指している参照の数より多い。これは**確定的なRC配置バグ**で、
  無害な説明があり得ない。
- 保守的スキャンでは死んでいて、参照会計では生きていて、他の追跡対象
  からは到達できる → ただの循環参照。想定内であり、バックストップが
  存在する理由そのもの。

前者は**偽陽性がゼロ**である。通常のプログラム構造からは決して生じ
ないので、1件出れば必ずバグだ。この分類器の上に、debug（かつ
non-LTO）ビルド限定・CI専用のリーク検出器が乗っている: 全オブジェクト
の生成時backtraceを記録し、慎重に選んだ1つの静止点で分類器を走らせ、
見つかれば生成箇所を添えてabortする。その静止点とは、トップレベルの
実行が終わり、moduleとnamespaceのrootはまだ配線されている瞬間だ。
「refcountが過剰で他は死んでいる」が「まだ到達可能と観測されて
いないだけ」ではなく確実に「リークしている」を意味する、唯一の地点で
ある。これがコンフォーマンステスト全体（例外throw経路を含む）に対して、
CIの常設フェーズとして回っている。出荷ビルドではabortしない。abort
自体がサービス拒否のベクタになりうるからで、そちらは静かに回収を
続ける。

もう1つ、診断用のトグルがすべてのcollectionを無効化する。ここで効いて
くるのは、1つのrefcountが実は2つの別々の仕事をしている、という切り
分けだ — **所有権**（いつ解放するか）と**ルーティング**（何をcollection
をまたいで生かすか）である。collectionを止めた状態で**残る**クラッシュ
はルーティングの問題ではありえない（何も回収されていない）ので、純粋な
所有権のバグ — 生きている値が解放された — だと分かる。**消える**
クラッシュは逆にrootの取りこぼしだったことになる。実際にはこの方法で
調べたクラッシュのほぼ全部が前者だった。rootの探索が原因だったのは
1度だけで、しかもそれを表に出したのはエンジンの切り替えである。
executorが既定になったあと、wasmのPlaygroundが生きている値を失い
はじめた。文字列は参照カウントを持たず、tracingだけで回収される。
既定を切り替えたことで、この表現が、保守的なスキャンにrootの見えない
唯一のビルドに持ち込まれてしまったのである。直し方は、上に書いた
safepointの仕組みだ。

コレクタ側にはストレスモードもある。適応的なスケジュールの代わりに
**すべてのアロケーションで**collectするので、タイミング依存で
気まぐれに現れるバグが決定論的に表面化する（SpiderMonkeyの`gcZeal`と
同じ発想）。フルなコンフォーマンススイートはこのモードでも緑で走る。

## 払っている代償

この立ち位置は無料ではない。

**トップレベル束縛は`drop`されない。** `drop`を持つオブジェクトを
トップレベルに束縛すると、どのレーンでもプログラム終了まで生き残り、
`drop`は走らない。プログラムの終了時にトップレベルの束縛は解放される
が、そのとき`drop`の呼び出しは意図的に止めてある。もともとこれは、
tree-walkingインタプリタがたまたまそうなっていた、というだけの話
だった。そこに束縛された関数がその環境自身を捕捉するので、環境全体が
1つの大きな循環参照になり、破棄されなかったのである。コンパイルする
レーンは、動きを揃えるためにそれに合わせていた。いまはその出どころの
エンジンが無くなり、これ自体が規則になっている。スクリプト全体にわたる
リソースには`defer`か明示的なクリーンアップを使うことになる。ここは
Rustと同じ側の判断でもある — Rustの`static`もdropされず、そもそも
デストラクタが走ることを保証しない（`mem::forget`は`unsafe`ですら
ない）という立て方で、プロセス終了時の後始末は言語の仕事ではないと
している。Swiftのグローバルも`deinit`されない。culebraが両者と分かれる
のは終了時ではなく循環のほうで、そちらは言語が引き取る。

**クロージャだけが作る循環と、極端に大きなカスケードはGC送りになる。**
resourceからの逆参照が無いclosure専用循環（再帰local `fn`が捕捉する
形など）は決定的な窓を外れ、バックストップのタイミング — collection
駆動で、`GC.stat()`で強制できる — で発火する。同じ扱いになるのが、
1つのスコープが数千単位の循環所有オブジェクトを一度に手放した場合の
超過分だ（カスケードには通常のプログラムを同期的に保つためのサイズ
上限がある）。どちらもfinalize順序は未規定で、プログラム終了まで
生き残った孤児はメモリだけ回収されて`drop`は走らない。決定性が保証
されるのは、この節に挙げた形を除いた範囲だという但し書きが付く。

**保守的スキャンは過剰保持し、movingは永久に諦めている。** 偽rootは
有界とはいえ実在し、死んだものが1collection余分に居座ることはある
（生きているものが誤って解放されることはない）。non-movingの決定が
動くのは、断片化が実測で問題になるか、生ポインタの相互運用をハンドル
かpinningの背後に再設計したときだけだ。

**実行時コストを二重に払っている。** 機構を2つ持つ以上、値を触る
たびのrefcount操作と、定期的なmark-sweepの両方が乗る。片方だけの
言語ならどちらか一方で済む話だ。しかもtracing側は非世代別なので、
1回のcollectionは毎回ヒープの生存部分を丸ごとたどる — 世代別なら
minor collectionは若い世代だけで済むが、これは純粋なスループット
最適化なので、非世代別のベースラインでは足りないと計測されてから
足す方針にしてある。`shared_ptr`を捨ててretain/releaseを明示的に
配置しているのは、この二重コストの片方 — 値に触れるたびの
アトミックなrefcount操作 — を削るためで、その代償として払っているのが
上に書いた所有権規律である。コレクタ側で実測して潰した分もあって、
per-objectの帳簿を置くレジストリのアロケーションchurn（12〜21%）は
flat hash mapへの置き換えで解消済みだ（internals §6.3）。

そして最後に、いちばん大きなもの: **処理系側のコード量と複雑さが
大きい**（実行速度の話ではなく、作り込みの話である）。GCだけの言語
ならコレクタ1つで済み、RCだけの言語ならユーザーに`weak`を書かせれば
済む。culebraは両方を持ち、しかも2つのレーンで外から見える動きを
揃えなければならず、さらに「RCのバグをGCが隠す」問題を埋めるための
検出器まで持っている。ユーザーが書かなくてよくなった`weak`の1語は、
処理系の側にこれだけの構造として現れている。それでも割に合っていると
考えているのは、`weak`の書き忘れがユーザーのプログラムで起こす失敗は
静かで再現しにくいのに対し、処理系側の複雑さは1箇所に集約でき、CIで
毎日検査できるからだ。この規律には数の管理も付いていて、規律の外に
残っている手書きのretain/releaseは監査済みの移行債務として数えられ、
増やすことは許されていない。

## 系譜

この設計はどれか1つのシステムを丸ごと採ったものではない。culebraの
codegenには独自のborrow checkerがなく、whole-program型推論を持つ
関数型IRではなく動的なASTをloweringするので、以下のどのシステムも
そのままは転用できなかった。各所から1つずつ構造的なアイデアを借りて
いる。

| 出どころ | 借りたもの |
|---|---|
| C++ RAII | 実装の乗り物そのもの。デストラクタが解放を発行するハンドルは、早期returnや例外をまたいでも自動的に正しい |
| Rust（affine ownership、`Drop`） | move-or-consumeを値の基本規律にすること。借用は分類上決して解放されない |
| Swift ARC | retain/release配置を1箇所ずつ判断せず、1つの一貫した規約から*導出する*という発想 |
| CPython | 精密なサイクル検出（`gc_refs`減算）と、finalizeをsweep前に行うPEP 442の順序 |
| Perceus（Koka） | 精密で決定論的なdropを持つ参照カウント設計の中で、構造的に最も近いもの |
| Nim（ORC） | 「RC主体 + サイクル回収backstop」が理論上の妥協ではなく出荷可能な組み合わせだという裏付け |
| Boehm GC・Ruby | 保守的なスタックスキャンが最適化コンパイラの下でも健全である論拠 |
| SpiderMonkey（`gcZeal`） | アロケーションごとにcollectして、タイミング依存のバグを決定論に変えるストレスモード |
| MLIR / Swift SIL ownership | 目指している到達点。所有権が、レビュアーが目視で守るコメント上の約束ではなく、中間表現がチェックできる性質であること |

## まとめ

culebraのメモリ管理は、「RAIIとGCのどちらが正しいか」という問いに
答えを出していない。**リソースにはRAIIが要る。循環にはGCが要る。
だから両方積む** という、答えを回避する形の設計になっている。ユーザー
から見えるのは、`}`でファイルが閉じることと、親を指し返しても何も
起きないことの2つだけだ。

その裏側を一言でまとめるなら、**ユーザーに渡しているRAIIを、処理系
自身の実装でも使っている**、という入れ子になる。設計として一貫して
いるかどうかは、たぶんこの入れ子がどこまで保てるかで決まる。
