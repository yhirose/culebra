## 1. 参照カウントが主、tracingがbackstop

culebraのメモリ管理は**参照カウント（RC）が主で、tracingコレクタが
backstop**である。2つのエンジンレーン — バイトコードexecutorと
LLVM lowering — は1つのランタイム、1つのヒープ、1つのコレクタを
共有する。設計のどちらの半分も、もう一方に代えて退役させることは
できない:

- **RCだけではリークを避けられない。** 参照サイクル（`a.c = a`）は
  各メンバのカウントを永遠にゼロより上に保ち続ける — どれだけ正しく
  RCを配置しても回収できない。これはculebra固有の問題ではない —
  SwiftのARCは、プログラマの誤りが入り込む余地のないコンパイラ
  完全生成であってもretain cycleを日常的にリークする。「体系的な
  RCで十分」という主張の標準的な反例である。
- **tracingだけでは決定的な`drop`を与えられない。** tracingコレクタ
  はcollectionを実行したときに初めてオブジェクトが死んでいると
  発見する。最後の参照が消えてから次のcollectionまでの間、
  オブジェクトは不活性だが未だfinalizeされていない — したがって
  `drop`は遅く発火し、しかもコレクタのsweepがオブジェクトを訪れる
  順序で発火する。GoとJavaのfinalizerはまさにこの通りに振る舞い、
  だからこそどちらの言語も決定的な破棄を提供しない。共有所有権の
  下での決定的なfinalizationは、正確な参照カウントによってのみ
  可能である: カウントがゼロに達すること自体が信号であり、最後の
  参照が解放された瞬間に起こる。

つまり2つの機構は異なる2つの問いに答える。RCはオブジェクトが*いつ*
死ぬかを決め、`drop`のタイミングを駆動する。tracingコレクタは
*RCにできないこと*に答える: サイクルを回収し、backstopとして、
参照カウントの配置ミスがあれば永遠にリークしていたはずのものを
回収する。

手動の参照カウントには誤り方がちょうど2つある:

- **解放の失敗**（リーク）: あるコードパスがデクリメントし損ねる
  ことで、オブジェクトがすべての参照より長生きしてしまう。
- **余分な解放**（use-after-free / double-free）: あるコードパスが
  自分が所有していない参照をデクリメントすることで、まだ生きた
  参照があるうちにオブジェクトが解放されてしまう。

すべての制御フローパス — fall-through、`break`、`continue`、早期
`return`、複数のスコープを貫く例外のunwind — にわたって配置を
手作業で正しくするのは難しい。この文書の残りは、配置が起きる3つの
場所と、それぞれがどう正しく保たれているかについてである。

## 2. 参照カウントはどこに置かれるか

ホットパス上には`shared_ptr`が一切ない: retainとreleaseは明示的な
操作であり、これを配置する場所が3つある。

**バイトコードコンパイラ。** `vm::Compiler`は`Retain` / `Release` /
`Take`を命令列にemitし、2つの消費者 — executorとLLVM lowering —
はそれを実行するだけである。したがってコンパイラの配置がもっとも
重要であり、1回だけ検証される: すべての式は結果レジスタに`+1`を
残し、文の一時値は文末でsweepされ、throwはchunkごとのunwindテーブル
（スコープのslot範囲と各pcでの実行中の一時値）から*borrowオペランド
契約*の下で解体される — 演算子やヘルパーはオペランドをborrowする
ので、throwはすべてのレジスタをフレーム所有のまま残し、テーブルが
唯一の解放者になる。[`vm.md`](vm.ja.md) §5.2と§5.5がこの形式を
説明しており、この文書の§5にあるゲート群が両レーンでこの配置を
検証する。

**LLVM lowering自身のcodegen。** 1つのバイトコード命令をlowering
することは、しばしば複数のLLVM値が同時に飛び交うことを意味する —
別の呼び出しをまたいで保持されるヘルパーの結果、コンテナに渡される
値、メソッドが動く間borrowされるreceiver。これらの一時的な`+1`は、
IRが構築されている間`struct JIT`内のC++オブジェクトであり、その
解放はコンパイラでなくloweringがemitする。§4がそれらの配置を構築
によって正しくする規律である。

**ランタイムのヘルパー。** 値を渡される`culebra_runtime_*`ヘルパー
は閉じた所有権契約の集合（§4.3）のうち1つに従い、そのC++コードは
2つのRAII形式を使う: `JitOwnedVal`（消費されない限りすべての出口
で解放される所有ローカル）と`JitUnwindRelease`（ヘルパーがthrowした
場合のみ実行される解放）。

## 3. 値表現

値は16バイト、`JitValue { int64_t tag; int64_t data; }`である。
参照カウント付きヒープ構造体 — `JitClosure`、`JitArray`、
`JitObject`、タプル、set、tensor、captureされた変数を箱に入れる
`JitCell` — はすべて`int64_t refcount`をoffset 0に持つので、
retainまたはreleaseはどちらのレーンが行っても1回のメモリ操作で
ある。文字列は例外である: `TAG_STRING`と`TAG_STRINGVIEW`は
refcountがあるはずの場所にインラインの長さヘッダを運び、tracing
コレクタだけによって回収される（§6）。Nil、Bool、Long、Floatは
即値である。

オブジェクトはper-`Runtime`のスラブアロケータ（`jit_slab.h`）から
割り当てられる: サイズ別に分離され、64 KBのchunkを切り出し、
moveせず、ロックフリーである — なぜなら`Runtime`（そしてそれに
伴うヒープ、コレクタ、deferスタック、例外キャリア）はスレッドごとに
1つだからである。コレクタ自身のper-objectメタデータはオブジェクトの
外側、アドレスをキーとするレジストリに置かれる（§6.3）ので、
retain/releaseのコードは自分が所有していないヘッダに一切触れない。

決定的な`drop`は同じカウントに乗る: refcountがゼロに達した
オブジェクトは、その子が解放される前に`drop`を実行する。`drop`を
持つオブジェクトは`drop`が束縛された瞬間からper-`Runtime`の
*owned stack*（`jit_owned.h`）にも登録される。スコープを抜けると
そのマークより上のエントリが解決されるので、スコープ内でサイクルに
逃げ込んだdrop持ちオブジェクトでも、スコープ境界で`drop`される
（`culebra_runtime_owned_scope_exit`）。契約全体 — タイミング、
順序、プログラム終了時の抑制 — は`language.md` §17にある。

## 4. LLVM loweringの所有権規律

### 4.1 目標

生成されたコードにおけるリークとdouble-freeは**構築によって**
防がれなければならない — C++でRAIIが`delete`忘れを防ぐように、
Rustでaffine ownershipがuse-after-moveを防ぐように — 1箇所ずつ
見つけてパッチを当てるのではなく。個別サイトへのパッチは収束
しない: 修正のたびに、次のまだ監査されていないコードパスが同じ
誤りにさらされたまま残る。

ヒープ値を生成または消費する新しいcodegenは、以下で説明する所有権
レイヤーを必ず通らなければならない。*新しい*コードパスにおける
素の手書きretainまたはreleaseの呼び出しは、正当な実装選択ではなく
レビューで正当化すべき欠陥として扱われる。`tools/checks/check_rc_discipline.sh`
は`jit.h`内のそうしたサイトの数をratchetし、減る一方であることを
強制する。

### 4.2 所有権とルーティングは別の仕事である

1つのrefcountが同時に2つの独立した仕事をしており、それらを混同
することが「このretainは冗長に見えるから消す」という素朴な編集を
危険にする:

1. **所有権/解放**はオブジェクトが*いつ*解放されるか
   （release-to-zero。これは`drop`を発火させるものでもある）を
   決める。
2. **ルーティング/生存**は*何がcollectionをまたいで生き残るか*
   を決める。

2つ目の仕事は、個々のretainとは独立に、コレクタの保守的なroot
スキャン（§6.2）が処理する: スタックフレームやレジスタウィンドウ
に保持された値は、そこにあるという事実だけでrootになる — ただし
refcountの会計が正確であることが前提であり、それはまさに以下の
規律が確立するものである。したがって「冗長に見える」retainを
消すことは決してルーティングの問題ではない。その値の参照カウント
のすべての生成者と消費者を辿る完全な会計の証明を必要とし、新しい
ルーティング機構を追加することでは決してない。

常設の診断が2つの失敗モードを区別可能にする: `CULEBRA_GC_NEVER=1`
はすべてのcollectionを無効化する。それでも**生き残る**クラッシュ
は — 何も回収されていないのだから — ルーティングの問題ではあり
得ず、過剰解放である。それで**消える**クラッシュはルーティングの
穴だった。この方法で調査されたクラッシュはすべて前者だったことが
判明している。

### 4.3 階層化された設計

以下の各レイヤーは、リークまたはdouble-freeが起きる方法をちょうど
1つずつ取り除く。組み合わせると、リークやdouble-freeを起こすには
C++の型またはRAIIの不変条件を破らなければならなくなる —
コンパイルエラーであって、静かなランタイム事故ではない。

**統一された規約。** 式をloweringする関数はすべて、呼び手が
1参照を所有する値（`+1`の値）を返す。パラメータやメソッドの
receiverは*borrow*される（`+0`）: 呼び手は呼び出しの前にretain
し、呼ばれた側は自分のコピーをretainするのでなく渡された参照を
消費する。スコープslotに格納された値は、その時点からそのslotの
所有物である。

**一時的な値のためのmove-onlyハンドル（`JIT::Owned`）。** ある
命令をloweringして生成され、次の命令に消費される`+1`の値は、
素のポインタでなくmove-onlyのRAIIハンドルに保持される。この
ハンドルは3つの操作を公開する: `borrow()`（消費せずに読む）、
`consume()`（参照をちょうど1回、slot・呼び出し・returnへ渡し、
ハンドルを使用済みにする）、`drop()`（渡されるのでなく死ぬ値を
即座に解放する）。**すでに使用済みのハンドルを消費することは
コンパイル時のabortである** — double-freeがビルド失敗に変わる。
ハンドルがスコープを抜けるときにまだ参照を保持していれば、その
デストラクタがそれを解放する。このハンドルがカバーするのは
*直線的な*コード領域だけである。ループの反復をまたいで生き
なければならない値、あるいはある分岐で消費され別の分岐で解放
される値は、次のレイヤーを必要とする。

**直線的な領域を脱出する値のためのスコープslot。** 自分の発生
領域より長生きしなければならない値は、スコープslotに消費される。
スコープunwind機構はそのslotを*すべての*出口パス — 通常の
fall-through、`break`/`continue`、早期`return`、そして例外unwind
（最後のものはregionごとのcleanup landing pad経由。その領域が
throwし得ないと証明できれば削除される）— で解放する。同じ機構
が、字句ブロック、ループ本体、`match`/`try`本体、`for`ループの
iterable用スコープ、関数フレーム自体という、すべてのスコープ様
領域を一様にカバーする。

**関数フレームのunwindパスは1枚のpadでなくladderである。**
フレームはthrowするすべての呼び出しが後退するregionなので、
これに単一のlanding padを用意すると、呼び出しごとに1本のunwind
edgeを集め、フレーム内のすべてのslotを読むことになる — これは
コンパイラにedgeごとslotごとのmerge valueを要求し、関数のサイズに
対して2乗のコストになる。代わりにフレームの後始末は所有される
束縛ごとに1段の踏み段に分割される: ある呼び出しは、それが立って
いる時点で生きている束縛のための踏み段へunwindし、その踏み段は
自分のslotを解放してから1段下へ落ちる。踏み段はその束縛の初期化
storeより後からしか到達できないので、merge valueは一切不要で
あり、ladderを下る解放順序は通常の出口が使うのと同じ逆宣言順で
ある。トップレベルもここでは普通のフレームである — プログラム
自身の束縛は、捕捉されなかったエラーがそれを去るとき、関数の場合
と同様に解放される。

**例外オブジェクトもリソースであり、throwを終わらせるpadだけが
それを保持する。** 例外を*処理する*landing padはそれをC++ ABI
経由で開き（`__cxa_begin_catch`）再び閉じる（`__cxa_end_catch`）—
その対になった操作こそが例外オブジェクトを解放するものである。
ABIはhandler countがゼロに戻ったときにそれを回収するからである。
あるregionの解放だけを行いthrowを先へ渡すpadは決してそれを開か
ない: カウントはthrowからそれを終わらせるpadまで手つかずのまま
移動するので、cleanup padには均衡させるものが何もなく、何かを
座礁させる方法もない。これはClangがcleanupをemitする方法でも
あり、throwのコストをpadの数ではなく横切るフレームの数に比例
させ続ける。

この2種類は1つのemitterによって作られ、そこで選択が行われる。
cleanup region — そのlanding pad、その解放群、throwを先へ運ぶ
唯一のedge — は1つのオブジェクト（`JIT::CleanupPad`）であり、
そのデストラクタがそのedgeをemitするので、regionは継続される
ことなしに開かれることがない。handlerは`emit_handler_prologue`
によって開かれ、処理された腕で、あるいはre-raiseする場合は
rethrow自身のunwind edge（`emit_handler_rethrow`）で閉じられる。
組にし忘れは、あらゆる値レベルのリークチェックからは見えない —
座礁するのはculebraの値でなくC++の例外オブジェクトだからである。
そこで`tools/checks/check_eh_balance.sh`がemitされたIRを読む: handler
のprologueだけが例外を開いてよく、すべてのrethrowはそれを閉じる
unwind edgeを持つ。

**borrowされた値は解放操作を一切公開しない。** borrowされた値の
ハンドルは読み取り操作だけを提供する — 同じ値をborrowかつrelease
するAPIは存在しない。「borrowされたオペランドがreleaseされた」
はしたがって表現不可能なバグである — その呼び出しを引き起こし
うるメソッド呼び出しが型システムに存在しない。

**自動的なunwind-tempウィンドウ。** `Owned`ハンドルはC++の
デストラクタ経由で解放する — これはランタイムでLLVMレベルの
`throw`が実行できない。生成されたコードをunwindするのであって、
C++のスタックフレームをunwindするのではないからである。その
ハンドルに保持され、throwし得る呼び出しをまたいで生きている値は
どれも、その正確な形のためのガードが手で置かれていない限り例外
パスでリークする — そしてどんな有限のテストコーパスもすべての
形を網羅することはない。したがってunwind edgeは列挙するのでなく
構造的にされている: すべての生きているハンドルは作られた時点で
`JIT`に自分自身を登録する。`emit_call`はthrowし得るすべての
呼び出しを`invoke`に変え、その周囲（`open_unwind_window` /
`close_unwind_window`）で、まだ生きていて他のどこにもカバーされて
いないハンドルはすべて、すべてのcleanupパスが最初に解放する
per-function cleanup slotへspillされる。以下の契約のどれか1つ
にすでにカバーされている値はそのようにマークされスキップされる —
これがそのウィンドウがそれをdouble-freeすることを防ぐ。

**ヘルパー呼び出しを横切る値の所有権契約。** ランタイムヘルパー
への呼び出しをまたいで所有権が移転しなければならない値は、閉じた
契約の集合のうちちょうど1つに従う — 決して2つ以上ではない。同じ
値に2つのcleanerが割り当てられることは構築によってdouble-free
だからである:

| 契約 | unwindパスで誰が解放するか | 使われる場所 |
|---|---|---|
| Caller-cleans | 呼び出しサイトのregionごとのcleanup pad（`ThrowGuard`）。regionがthrowし得ないと分かれば削除される | 組み込みメソッドのreceiverと引数、呼び出しのcallee式、代入のターゲット、UFCSのcallee |
| Callee-cleans-on-throw | ヘルパーの本体全体を覆うガード（`JitUnwindRelease`）。すべてのthrowが呼び手の一時値を解放する — user-dispatchウィンドウと直接エラーの両方 | 演算子の実装、receiver所有下でのindex/property access、not-a-functionエラーパス |
| Callee-consumes-on-every-exit | ヘルパーの入口で宣言される所有引数ハンドル（`JitOwnedVal`）。通常returnとunwindの両方で解放する | ネイティブメソッドのエントリポイント、高階関数のaccumulatorとcallback |
| Borrow-neutral invoke | 呼び出し元がcalleeが消費する参照を鋳造し他には一切触れないので、本体がreturnしてもthrowしても呼び出しはrefcount中立である | ユーザー定義dispatchが走るすべてのウィンドウ — 演算子オーバーロード、`eq`/`hash`/`cmp`、`__index__`、プロパティのgetter |
| Transfer | 渡ってきた参照がそのまま返されるか、capture cellやslotに直接渡される | イテレータ自身のメソッド、遅延構築されるcombinatorのcapture cell |

最後の2行は両側から見た同じ1つの規則であり、その分割には意味が
ある: dispatchウィンドウはしばしば*コンテナ*が所有する値を渡さ
れる — comparatorが走る間のarrayのslot、lookup中のdictionaryの
格納されたキー — このとき解放すべき呼び手側の一時値はそもそも
存在しない。unwindパスで解放するinvokerはそれらの要素を、所有者
の足元から解放してしまう。したがってcleanupは`+1`を鋳造した者に
属し、共有dispatchヘルパーには決して属さない。

**素の参照は生成されたブロックに閉じ込められる（`Pinned`）。**
最後の抜け道は、参照がハンドルを離れる瞬間である。`Owned`から値を
読み出すと、以前は何にも追跡されないままbasic-block境界を越え
られる素のLLVM値が得られていた — その時代に見つかったリークは
すべてこの形だった。代わりに採用された規則: 素の参照は、それが
生成されたbasic blockの内側でのみ使ってよい。これは健全かつ完全
である。なぜならthrowし得るすべての呼び出しは`invoke`として
コンパイルされ、それは必ず自分を含むブロックを終端させるからで
ある — したがって「まだ同じブロック内」はすでに「その参照が生成
されて以来unwind edgeは1本も走っていない」を含意する。
`consume()`は自分の起源ブロックを記録する`Pinned`トークンを返し、
別のブロックでそれを使うとすべてのビルド構成でabortする
（`rc_pin_violation`）。したがってその誤りは、コードが実際に
*実行された*ときではなく*コンパイルされた*瞬間に捕まる。真に
ブロックを横切る形の一握り（phiに収束する互いに排他的なdispatch
の腕 — `OwnedPhi`、すでにスコープslotに所有されている値、local
を宣言するprologueの転送）は`consume_unchecked()`を使い、それぞれ
が自分自身の宣言された解放者を持つ。そうしたサイトの数はratchet
される。サブ式をloweringするすべての関数は、素の参照でなくこれら
のハンドルのどれか（失敗時は空のもの）を返す — したがって素の
`+1`がloweringのステップ間でC++の関数return境界を越えることは
決してない。

### 4.4 「正しいcodegenはリークしない」が帰着すること

§4.3のすべての規則が成り立てば:

1. すべての一時的な`+1`の値はハンドルに保持されているか、すでに
   消費されている。
2. ハンドルはちょうど1回消費されるかちょうど1回解放される —
   move-onlyの型とそのデストラクタと二重消費abort規則が「両方」
   や「どちらでもない」を表現不可能にする。
3. 自分の発生領域を脱出するすべての値は、ちょうど1つのスコープ
   slotに消費され、スコープunwindはすべての出口パスですべての
   slotを解放する。
4. borrowされた値は決して解放されない。borrowされたハンドルに
   そのような操作が存在しないからである。
5. ルーティングはコレクタのroot scanが提供し、所有権のrefcount
   とは独立である（§4.2）。
6. サイクルと残余のリークはtracing backstop（§6）が回収する。
   backstopは定常状態のメモリ挙動に依存されない — 所有権が
   正しければ、実際に仕事をするのは稀である。
7. throwし得る呼び出しをまたいで生きているすべてのハンドルは、
   unwindパスにちょうど1つの解放者を持つ: 既定の自動spill
   ウィンドウか、宣言された所有権契約のどちらか — 両方では
   決してない。
8. 素の参照は生成されたブロックの内側にだけ存在する。意図的な
   例外はすべて宣言され監査されたサイトである。
9. サブ式をloweringする関数は、自分自身のreturn境界を越えて素の
   参照を返さない。

系: codegenパスがリークまたはdouble-freeを起こすには、これら
9つの不変条件のどれか1つを破らなければならない。それぞれがC++の
型かコンパイル時チェックによって強制されている — テストで捕まえる
ランタイム上の事故ではない。この規律の外に残る手書きのretain/
release呼び出しは監査済みの移行debtであり、数えられ増えることを
決して許されず、handleレイヤーがカバーするつもりのない少数の正当
な範疇に入る: 生成されたループ本体内でのイテレーションごとの
解放、handleレイヤーの*下に*座るslot/scopeの基本要素、直線的な
一時値としてではなくパラメータの連鎖として下方へ運ばれる値、
そしてある腕が値を消費し別の腕が解放するような分岐をまたぐ
consume/release対。

### 4.5 この実装に固有の制約

- **値はタグ付き64ビット整数であり、型付きポインタではない。**
  ある値がそもそもヒープポインタかどうかを判断するにはtagを
  読む必要がある。これと、C++相互運用（Tensor、エンジン境界の
  横断）へ逃げる素のポインタが組み合わさって、LLVM Statepointを
  使うmovingコレクタがルーティング機構として採用されなかった
  理由になっている（§6.4） — それをサポートするには、この所有権
  規律よりはるかに大きな値表現の書き換えが必要になる。
- **2つのレーンは振る舞い上対称であり続けなければならない。**
  この規律への変更は構築上内部的なものであり、executorや、
  ゲート群が差分を取る対象のリリース済みバイナリに対して、観測
  可能な振る舞い・エラーメッセージ・チェックが走る順序を決して
  変えてはならない。
- **dispatchは実行時に解決される。** メソッドと演算子のターゲット
  は静的には分からないので、所有権契約はcalleeの静的な型によって
  ではなく、呼び出し境界で動的に強制される。
- **関数全体のIR verifierは検討され却下された。** そのような
  verifierはC++ヘルパー関数の内部に対して盲目であり、「すべての
  retainがreleaseと対をなす」は「すべての値が必要な期間だけちょうど
  生きていた」を含意しない — 早すぎるが均衡の取れたreleaseでも、
  生きたuse-after-freeの窓を残しうる。§4.3のブロック閉じ込め規則は
  意図的により狭い範囲にある: それはこの規律自身のハンドルについて
  のみ推論し、ヒープのエイリアシングや一般的なオブジェクトの生存
  については推論しない — これこそが、関数全体verifierを沈めた
  異論を回避できる理由である。

## 5. 参照カウントのバグを検出する

検出されずに残った参照カウントの配置バグには、特有の役に立たない
失敗の兆候がある: tracing backstop（§6）が次のcollectionで静かに
リークしたオブジェクトを回収してしまい、その誤りが表に出ることは
二度とない。以下の検出器群は、配置バグが出荷後の高いメモリ使用量
としてでなく、ゲートの失敗として現れるようにするために存在する。

### 5.1 参照会計による分類器

CPythonの`gc_refs`アルゴリズムはこのヒープの上で実行できる
（`Heap::compute_gc_refs`）: 追跡される各オブジェクトについて、
そのrefcountから始め、別の追跡対象オブジェクトが保持する参照
ごとに1を引く（子を辿って見つける）。残ったものがヒープの*外側*
にあるもの — スタックの値、グローバル、borrow — から寄与された
カウントである。`CULEBRA_GC_REFS=1`はこれをコレクタのroot探索
にする（正の残余を持つオブジェクトから種をまき、スタックスキャン
は一切行わない）。この答えを、同じヒープに対する保守的スキャナの
答えと比較すると、2つが不一致となるすべてのオブジェクトが分類
される:

- **保守的には死んでいるが`gc_refs`は保持しており、他の追跡対象
  オブジェクトからのみ到達可能**: 参照サイクルである — 予期された
  もので、backstopが回収するために存在するまさにそのものである。
- **保守的には死んでいるが`gc_refs`は保持しており、他の追跡対象
  オブジェクトから到達可能では*ない***: そのオブジェクトの
  refcountは、それを指す実際の参照の数より多い。これは確実な
  配置バグ — 解放漏れ — であり、無実の説明はあり得ない。

2つ目の範疇は**偽陽性ゼロ**のリーク検出器である: 会計の誤りだけが
これを生成できる。`tools/analysis/gc_leak_check.sh`（`just test`
のrc-leakバッテリー）はパターンファイルを両方の方法で実行し、
生存カウントを比較する。

### 5.2 出荷前にリークを捕まえる

`CULEBRA_GC_LEAK_ABORT=1`はdebug/CI専用の検出器を武装させる: すべて
のオブジェクトは誕生時に自分のアロケーションのバックトレースを
記録し、1つの静止点 — トップレベルのプログラムは終了しているが
モジュールと名前空間のrootはまだ配線されている、「膨らんだ
refcountかつ死んでいる」が「まだ到達可能と観測されていないだけ」
ではなく明確に「リークしている」を意味する唯一の点 — で、
`Heap::maybe_audit_leaks`が分類器を実行し、見つかればリークした
オブジェクトの誕生地点とともにabortする。`tools/difftest/leak_abort_suite.sh`
はthrowパスも含めて生成コーパス全体をこの下で両レーンについて実行
する。abortしたケースはすべて`leak_abort_allow.txt`に名指しされて
いなければならず、そのリストは空である。この監査は非LTOビルドを
必要とする。LTOの変更されたスタックレイアウトは保守的なrootを
過小報告するからである。本番ビルドは、abortではなく静かにリーク
したオブジェクトを回収し続ける — abortは出荷されたバイナリにおいて
それ自体denial-of-serviceのベクタになってしまうためである。

### 5.3 成長ベースのリークfuzzing

`tools/difftest/leak.sh`（`just test`のleak-fuzz）は各コーパス
ケースをN回、`CULEBRA_GC_NEVER=1`の下で実行し — backstop offなので
RCリークがマスクされることはない — レーンごとの
`GC.stat().rc_objects`の成長を測る。判定はレーンごとの絶対値であり、
リグレッションのbaselineとして`leak_baseline.txt`に記録される: 成長
してリストにないケースは失敗し、成長しなくなったリストのケースは
ファイルを縮められるよう報告される。そこに保持されているエントリは
プログラム自身が書いた参照サイクル（`a.me = a`とその変種、相互
再帰的な`fn`宣言）であり、定義上永続的である — cycle collectorを
offにするとサイクルはリークするからである。新しいエントリは、
ファイルする前にプログラムの1辺を切ることで分類される: サイクル
の成長はゼロに落ち、漏れたretainの成長は落ちない。このゲートは
warm-upがthrowするケースを捨てるので、これは§5.2がその隣に存在
する理由である。

### 5.4 その他のレーン

`CULEBRA_GC_STRESS=1`はすべてのアロケーションでcollectを行い
（SpiderMonkeyの`gcZeal`モデル）、rootingやmarkingのバグを決定的
に表面化させる。対称性スイープと`vm_cases`はこの下で実行される。
`just test-assert`は`NDEBUG`なしでビルドし同じスイープを実行する
— 他のすべてのレーンは`Release`ビルドであり、ランタイムのassert
は決して実行されないからである。`CULEBRA_GC_NEVER=1`は§4.2の
診断上の判別器である。

## 6. tracing backstop

### 6.1 なぜ§4の規律だけでなくbackstopが必要か

§4の規律は正しく配置されたretain/releaseを新しいcodegenを書く唯一
の方法にするが、参照サイクルを解決することはできない — できるように
はならない。どんなRC規律にもできない、構築上の限界である
（Rustの`Rc`も全く同じ限界を持つ）。サイクルを回収する機構がなけ
れば、この形のリークは永続的である: サイクル構造を繰り返し構築
しては捨てる長時間稼働のプログラムは無限に成長する。純粋な
tracing（手動RCを完全に廃棄すること）は検討されたが§1で述べた
理由で却下された: それは決定的な`drop`を諦めることになる。したがって
RCが主であり続け、このコレクタの唯一の仕事はRCが構造的にできない
ものを回収することである — それに加えて、tracingのみの文字列
（§3）も。

### 6.2 保守的なroot探索

collectionが実行される瞬間（`Heap::scan_roots`）、ポインタとして
読んだときに有効なオブジェクトの開始アドレスに着地するすべての
マシンワードが候補rootとして扱われる。スキャナは値のtagを一切
参照しない — すべての8バイトワードを一様にテストするので、タグ
付き整数に保持されたヒープポインタも、そのタグが何であれ見つかる。
rootの出処は: collectionが実行される時点のスタックポインタから
スレッドのスタックベースまでの、mutatorスレッドの機械スタック
（`Heap::stack_base`。これはloweringされたフレーム、executorの
レジスタウィンドウ、すべてのC++ヘルパーのlocalsをカバーする）、
スキャン開始前に`setjmp`によってスタックへフラッシュされる
callee-savedレジスタ、そしてどのスタックの外側にも明示的に登録
されたroot — 名前空間テーブル、モジュールキャッシュ、REPLセッション
のcell、deferスタック、例外キャリア、マルチメソッド本体 — であり、
これらはランタイムのroot関数（`set_extra_roots_fn`）によって列挙
されるか個別にpinされる（`Heap::pin`）。

**なぜこれが健全か。** collectionを引き起こしうる呼び出しをまたいで
生きているコレクタ追跡対象のポインタは、プラットフォームの呼び出し
規約により、その呼び出しが行われる時点ですでにスタックへspillされて
いるかcallee-savedレジスタに保持されているかのどちらかでなければ
ならない — コンパイラがそれを置ける場所は他にない。collectionが
実行されるまさにその瞬間 — アロケータの奥深く、その呼び出しの
向こう側 — には、そのようなすべての値はスタック+レジスタスキャン
によってすでに見つかっている。これはBoehm流やRubyの保守的コレクタ
が、値を長い間レジスタに保持し続ける最適化コンパイラの下でも健全
であることを示すのと同じ論法である。それが成り立たない場所 —
wasm — ではコレクタは戦略を変える（§6.5）。

有効なヒープアドレスにたまたまエイリアスする非ポインタのスカラー
は**偽root**を生む — 実際には何も参照していないのにそれが指す
オブジェクトが生かされ続ける。これは境界のある過剰保持であり、
正しさの問題ではない: 健全性（§6.3）が要求するのは*生きている*
ものが決して解放されないことだけであり、過剰保持はそれに違反
しない。1つの細部が実際のデバッグ時間を要した: rootスキャンは
フレームポインタではなく**スタックポインタ**から始めなければ
ならない — `-O2`以上ではフレームポインタより下に生きるlocalsと
レジスタのspillが、そうしなければ完全に見逃されてしまう。

### 6.3 Collection: markとsweep

**オブジェクトモデル。** コレクタが追跡するすべての構造体は
offset 0に`int64_t refcount`を持ち続ける — retain/releaseのコード
はこれによって一切触れられない。コレクタ自身の記帳（markビット、
型タグ、サイズ）は別のレジストリ、`gc::GcRegistry`に住む。これは
per-entryのヒープアロケーションを持たないopen-addressingの
アドレス→ヘッダマップである。以前これに使われていた
`std::unordered_map`は、object-heavyなワークロードでコレクタが
追加していたアロケーションchurnオーバーヘッドの全量を占めていた。
可変長ペイロード（arrayの裏付けストレージ、objectのプロパティ
slot、closureのcapture）は構造体内の普通のC++コンテナに所有され
続け、sweep時にその構造体自身のデストラクタによって解放される。
したがってsweepの後始末はtype固有の特別な回収器ではなく、C++の
デストラクタである。

**トリガー。** `Heap::maybe_collect`はすべての登録で走り、2つの
閾値を持つ: カウントベースのもの（前回のcollectからのアロケーション
数を、生存集合に対して償却したもの — RCが小さく保つヒープ向けに
調整されている）と、バイト量ベースのもの（collect後の生存バイト
量に対する成長率 — これが唯一の回収者であるtracingのみの文字列
のために必要）。

**Mark。** root集合（§6.2）から始め、各型の子enumeratorを通じて
到達可能性を不動点まで推移的に辿る。保守的なrootは所定の位置に
pinされており — 何も移動しない — ので、事後のポインタ更新パスは
存在しない。

**Finalizeしてからsweep。** 何かが解放される前に、ランタイムの
finalizeフックが未markの各オブジェクトの`drop`をちょうど1回実行
する — 死んだ集合全体はまだ無傷で、そのrefcountはpinされている
ので、あるdrop本体が自分のsweepより先に兄弟を解放することはでき
ない（`language.md` §17が契約を述べている）。その後レジストリが
歩かれ、未markのすべてのオブジェクトのデストラクタが実行され
スロットが回収される。実際のroot集合からの完全なmark-and-sweepは、
refcountがどれだけ古くなっていようと、到達不能なオブジェクトを
すべて回収する — これがリークを永続的ではなく回収可能にしている
性質である。

### 6.4 なぜmovingでも完全に精密なコレクタでもないのか

movingコレクタは検討され、単に先送りされたのではなく明確に却下
された。2つの厳しい前提条件が満たされていないからである:

1. **精密なrooting。** 保守的なrootは定義上「ポインタかもしれない
   ワード」であり、そのようなrootはmoveの後にオブジェクトの新しい
   位置を指すよう更新できない — コレクタは元々それがポインタだった
   と確信を持てないからである。オブジェクトを安全にmoveするには
   精密なrootが前提条件として必要であり、保守性の傍らに追加できる
   ものではない。
2. **コレクタに非協力的なコードへ逃げる素のポインタが存在しない
   こと。** culebraはTensorやホストとの相互運用のためにC++へ素の
   ポインタを渡し、タグ付き整数の値表現（§4.5）はポインタを普通の
   整数に詰め込む — これはJITのrootを精密にする標準的な方法である
   LLVMのStatepoint機構が追跡できない表現である。これがCPython、
   Lua、Rubyの既定のコレクタがすべてnon-movingのままである理由と
   同じである。

movingが*唯一*提供するスループット上の利点 — 圧縮、そしてヒープの
サイズではなく生存者の数に比例する回収コスト — は、今日のculebra
にとっては二次的な関心事である。スラブアロケータ（§3）が、
どちらの前提条件も払うことなく、non-movingコレクタが達成可能な
スループットの大半を回復する。この判断を見直すには、ヒープの
断片化が現実的で実質的なコストであると測定するか、素のポインタ
相互運用をハンドルやpinの背後に置き直す別の再設計が必要になる
だろう。

`CULEBRA_GC_PRECISE_ONLY=1`と`CULEBRA_GC_ORACLE=1`はその問いの
ための開発モードである: 前者は精密な（非スタック）rootだけから
collectし、後者は保守的な生存集合のうちどれだけを精密なrootが
すでにカバーしているかを測る。

### 6.5 wasm上のsafepoint

wasm上では§6.2の健全性の論法は成り立たない: wasm locals — 値が
実際に生きているレジスタファイル — は線形メモリの外側に座っており、
`setjmp`はそこには何もspillしない。したがってアロケーションサイト
はcollectする安全な場所では決してない: 割り当てたばかりのオブジェ
クトも、ランタイムヘルパーがlocalにしか保持していない値も、
スキャンからは見えない。

`gc::kDeferToSafepoint`（`__EMSCRIPTEN__`でのみon）の下では、
inlineでのcollectionは一切走らない。閾値超過はpending flagを
立てるだけであり、バイトコードexecutorは命令境界で
`Heap::safepoint_collect()`をpollする — そこではすべてのフレーム
のすべての生きた値が、スキャンの見える線形メモリの配列である
レジスタウィンドウに収まっている。ただしこの移行でも残る危険が1つ
ある。2つのVMフレームの間で中断しているヘルパー（callbackが実行中の
イテレータop）が、自分自身のlocalsに唯一の参照を保持しているかも
しれない。不変条件は**そのようなフレームがスタック上にある間は
collectionを行わない**であり、1つの絞り口で強制される: helper
からuserへのすべての呼び出しは`_jit_invoke`（`jit_value.h`）を
通り、その`SafepointUnsafeScope`が呼び出しの間pollを延期する。
callee・receiver・引数を呼び出しの全期間レジスタに保つよう監査
されたdispatchサイトは`_jit_invoke_rooted`を使いcollectable
であり続ける — これが`Canvas.run`のゲームループを毎tick collect
させ続けるものである。markingは構築によってfail-safeである:
監査されていない新しい呼び出しパスは、次に適格なpollまでcollection
を延期するだけである。メモリは成長するが、誤って何かが解放される
ことはない。明示的なcollect（`GC.stat`）も同じようにゲートされる。
ネイティブビルドではこのプロトコル全体が消え去る。

### 6.6 安全装置

- `CULEBRA_GC_STRESS=1`はすべてのアロケーションでcollectする
  （§5.4）。
- `GC.stat()`は診断用に`live_objects`、`rc_objects`（参照カウント
  されたオブジェクトのみ — leak fuzzerが見るカウント）、
  `heap_bytes`を公開する。`CULEBRA_GC_BIRTH_SITE=1`はleak監査の
  報告用にオブジェクトごとのアロケーションバックトレースを記録
  する。
- §5のリークリグレッションゲート群がメモリ受け入れゲートを構成
  する。

コレクタ自身のC++実装は、自分が生成コードに強制するのと同じ規律
に従う: その後始末は普通の構造体のデストラクタであり、
stop-the-worldの調整はスコープガード（`CollectPause`）であり、
グローバルrootの登録はスコープの寿命に従う — 自分自身の実装の
どこにも手で対にしたsetup/teardownの呼び出しはない。

### 6.7 将来の世代別レイヤー

現在のコレクタは非世代別であり、今の形のままで正しい。世代別
レイヤー（若い世代をより頻繁にcollectし、remembered setで2つの
世代を橋渡しする）は純粋なスループット最適化であり、非世代別の
baselineがそれを必要とすると測定されてから初めて追加する価値が
ある — それ以前ではない。その唯一の厳しい要件を、まだ存在しない
がここに記録しておく。将来の実装を制約するからである: すでに
古いオブジェクトのフィールドへのヒープ値の格納はすべて、
remembered set内のwrite barrierによって記録されなければならない。
これがなければ、若い世代だけをトレースするminor collectionが、
そのようなold-to-youngのエッジを通じてのみ到達可能な若いオブジェ
クトを解放してしまうことがありうる。

## 7. 設計の系譜

§4の所有権規律は既存のどのシステムも丸ごと採用してはいない —
culebraのcodegenは自前のborrow checkerを持たず、全プログラム型
推論を持つ関数型IRではなく動的型付けのバイトコードをloweringする
ので、以下のどのシステムも直接は転用できない。それぞれが1つの
構造的な着想を提供している:

| システム | この設計が取り入れているもの |
|---|---|
| Rust (affine ownership、`Drop`) | 基本的な値の規律としてのmove-or-consume。borrowは分類上決して解放されない |
| C++ RAII | 実装の乗り物そのもの — デストラクタがreleaseをemitするハンドル。早期returnや例外をまたいで自動的に正しい |
| Swift ARC | 各サイトを手で置くのではなく、1つの統一された規約からretain/release配置を*導出する*という発想 |
| CPython (`gc_refs`) | §5.1の参照会計分類器、およびsweep前finalizationパス（PEP 442） |
| Perceus (Koka) | 精密で決定的drop、参照カウント設計の中でもっとも構造的に近いもの |
| Nim (ORC) | 「RC + cycle-collecting backstop」が単なる理論上の妥協ではなく出荷可能な組み合わせであることの実証 |
| Boehm、Ruby | §6.2の保守的root scanと、その背後の健全性の論法 |
| MLIR / Swift SIL ownership | この設計が向かっている到達点: 所有権が、レビュアーがコメントレベルの規約として目視で強制しなければならないものではなく、中間表現がチェックできる性質であること |

収束した形 — コンパイラがすべてのretain/release配置を1つの統一
された規約から導出し、どのcodegenパスも手で1つを書かない — は、
命令列に対してバイトコードコンパイラが行っていること、そして
loweringに対して§4がLLVM IR生成の上に層状のC++ RAIIハンドルを
使って実装していることである。
