# 2026-11-08 サックスの準備時間を実機Chromeで測る

- 見込み: 30分、コードの変更なし。実際: 約2時間。Chrome拡張の接続待ち、そして最初の測定が環境の影響を受けていた切り分けで使った。
- 結果（`harbor_lights.kau` を `alto_sax` で準備、52音、culebra-full）:
  - Node + wasm: 16.5〜17.1秒（2回）
  - userの普段のChrome 156: 19.1秒、16.3秒。ワーカー実行中のメイン側フレームの最大間隔は9ms（1回目に3250msの止まりが1度あったが、2回目は再現せず。原因は未確認）。
  - 私が拡張経由で操作するChrome（CDPが付いている）: 93〜96秒。**この数字は使えない**。同じ小さなベンチ（sin 300万回、配列、Audio.Graph）がNodeの3〜6倍遅く、userの普段のChromeでは Node と同じ速さだった。
- 学び: CDP を付けたブラウザの時間は、wasm の性能の測定に使わない。性能を測るブラウザは、デバッガを付けない普通のタブで、userに開いてもらって数字を報告してもらう（測定ページを `python3 -m http.server` で出して、結果は画面に出す）。最初に「同じ小さなベンチを Node と比べる」を置けば、2時間かけずに気づけた。
- 測っていないこと: メモリ、2回目以降の実行、ほかのブラウザ。
- 結論: ブラウザの準備は約16〜19秒でUIは固まらない。先読み再生の仕組み（S6の続き）を作る動機は「曲の頭を鳴らすまでの待ちを短くする」ことで、準備そのものの遅さではない。
