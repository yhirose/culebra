# Kauai: knobs in parentheses, and a JIT object cache between CI runs (2026-11-11)

- 規模: 大(書式の変更は全 .kau、docs 英日、tests、変換ツール、wasm)と、中(CI のキャッシュ)。担当(subagent)は /simplify の3並列だけ。実装は直列。
- 見積もりと実績: 書式の変更は半日足らず。時間の大半は `just dev`(約4.5分を2回)と `just site-build`(約6分を2回、/simplify の修正で作り直した)。CI のキャッシュは、実行の待ち(1回の全ジョブが約25〜40分)が支配した。
- 効いたこと: (1) 変更前のバイナリを退避し、全曲の `parse_file` と WAV のハッシュを新旧で比べた(13曲がビット一致、10曲は同じエラー、解析結果は全23曲で一致)。「音が変わらない」の根拠になった。(2) 変換スクリプトを `--write` の前に dry run して、全行を目で確かめた。(3) 逆変換(括弧を外して語を並べ替えて比べる)で、変換が括弧に包んだだけだと確かめた。(4) /simplify の担当が、括弧の中に `vol 10` を入れても通る不具合と、空の楽器名が通る不具合を、実際に走らせて見つけた(テストは修正前に落ちることも確認)。(5) CI は、同じコミットのジョブを再実行して(`gh run rerun --job`)、キャッシュあり・なしを同条件で比べた。
- 外れ: (1) 変換スクリプトの最初の版が、散文の「a drum needs its freq…」のような文にまで一致して、`kauai.cul` の文字列を壊した。楽器名を実在の名前(チップ名か大文字始まり)に限り、`src/` を対象から外して直した。dry run で全行を見ていなければ見逃した。(2) 旧書式を書き出す側(MusicXML の読み込みの `band_of`、テストの stub が楽器名とつまみを抜き出す2か所)を最初の洗い出しで取りこぼし、`just check` で落ちて初めて分かった。「声部の行を書く側」と「読んで抜き出す側」を最初に grep する。(3) ci.yml のステップに、`echo "jit cache: cold"` と書いて、YAML が `: ` を区切りと読んでワークフロー全体が無効になった(ジョブ0件の失敗、約25分の待ちを無駄にした)。workflow を触ったら、push の前に `python3 -c "import yaml; yaml.safe_load(...)"` で読めることを確かめる。(4) 待機コマンドが GitHub API のレート制限(5000回/時)に当たり、「失敗」と誤報された。待機は間隔を長くし、まとめて1回で読む。(5) 3つ目として、自分が起動した CI の結果を、あとの検証(ci/ ブランチ)が同じ木を覆うのに、完了まで待とうとした。ユーザーの指摘で止めた。
- 守備範囲の外で回した後処理: なし。`just site-build` は `kauai.cul` を触るたびに必要で、/simplify の修正で2回回した。
- 測定: CI のキャッシュ。ci-gc の vm/jit 全掃き(全340ファイル)が、冷えた実行で476秒、同じコミットの再実行(キャッシュ復元)で198秒(-58%)。レーン全体は1032秒から743秒(-28%)。gc-stress(約376秒)は実行が主なので変わらない。キャッシュは95MB、680ファイル、圧縮して20MB。ci-gc の実行時間は、キャッシュなしでも653〜1008秒とぶれる(同じ日の master の実行)ので、時間の比較は同じコミットの再実行でするのがよい。ci-light は JIT のコンパイルが少なく、キャッシュしても256秒のままだった(253秒が基準)ので外した。
- 未検証: (a) キャッシュ命中時の、ファイルごとのコンパイル時間の予算ゲート(60秒)の挙動。命中したファイルは測られず、変わったファイルだけが測られる設計(キーが最適化後の IR)だが、冷えた実行より検出力が下がらないかは、まだ実際の変更で見ていない。(b) master 上でのキャッシュの命中(ci/ ブランチのキャッシュは master からは見えない。master の最初の実行は冷える)。(c) linux-assert と test-macos のキャッシュ(未測定。arm64 は別のキャッシュが要る)。
- ユーザーの指摘: (1) 「Kauaiの `[duty=...]` の括弧の案」から、関数の引数の形 `pulse(duty=1/4 gap=2)` に決まった。つまみは楽器の引数と読める、という自然さが決め手。実曲の数(つまみ3つ以上の行は0本、同じ曲の中の重複は1か所)を数えて、宣言を曲ごとに持つ案(E)は見送った。(2) 「止めても問題ないCIを回した理由は?」。着地ごとの push で CI が自動で走ること自体は避けられないが、待つかどうかは、あとの検証が同じ木を覆うかで決める。
- 追記(ユーザーの指摘「まずmainに着地させて、CIを一度にしても問題ない場合もあるのでは?」): 着地3つ(書式、CIキャッシュの設定、書式の追加決定)を、着地のたびにpushして、全ジョブのCIが3本並んだ。同じ話題の連続した着地で、後続が依存せず、ローカルの着地は`just test-dev`を通っていたので、push1回で済んだ。根は、一覧(`.claude/orchestrate/project-culebra.md`の5節)の「pushは着地のたびに行い」の書き方と、ユーザーの「着地ごとにpushしてよい」の許可を毎回pushする義務と読んだこと。SKILL本体の原則3(固定費の大きい後処理はまとめて回す)と5節からは導けるので、本体は変えず、一覧の該当行を「pushの単位は束」に直した。あわせて、古いmasterのrunを`gh run cancel`で止めてよいことを書いた。もう1つ: 一覧を直すときに、main treeを直接編集してしまい(CLAUDE.mdは禁止)、気づいて戻してworktreeでやり直した。`.claude/`だけの変更でも、編集はworktreeで。
- スキルへの気づき: 書式の変更の束は、(a) 変換ツールを dry run、(b) 逆変換で等価を確認、(c) 書き出す側と抜き出す側の grep、(d) 旧バイナリの出力の保存、の4点を最初に置く。待機は、同じ API を叩くので、間隔を長くしてまとめて読む。
