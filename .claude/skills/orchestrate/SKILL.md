# 作業の段取り

目的は、与えられた問題を**正しく、エレガントに、安全に、そのうえでできる限り速く** 解くこと。速さのために前の3つは削らない。

最初に、そのプロジェクトの一覧（`references/project-<名前>.md`。culebraでは`project-culebra.md`）を読む。この本文は原則と手順だけを持ち、資源の容量、後処理の特性表、コマンド、決まり、見積もりの数字は一覧が持つ。一覧がなければ、最初の大の仕事で、直列の資源と後処理の特性表だけを測って作る。事例は`references/cases/`。

決まりの優先順位は、userのその場の指示 ＞ プロジェクトの決まり（指示ファイル、メモリ、一覧）＞ この本文。userが「判断はおすすめで」と言っているときも、仕様や振る舞いが変わること、戻せない操作、範囲の拡大、目的どうしの交換（速さとメモリなど）は聞く。それ以外はおすすめで進め、選んだことを報告に書く。

## 1. 原則

仕事は、資源を使い、時間がかかり、何かを確かめる作業の並びである。

1. **完了までの時間は、直列の資源を通る流れで決まる。** 直列の資源とは、同時に1つずつしか進まないもの。典型は、手元のマシン、CIの枠、着地、人の判断（user、レビュアー）、自分の注意と文脈。担当を増やしてもこの流れは縮まず、取り合いと統合の分だけ伸びる。だから直列の資源は、空けず、重ねずに使う。
2. **基本は直列。** 並列にするのは、分けた方がはっきり早いと見積もれたときだけ。見積もりには、分けたことで増える後処理、資源の順番待ち、統合（rebaseと衝突の解消）を入れる。直列の資源を使わない作業（調査、設計、書くこと）は並べやすい。同じ直列の資源を長く占める変更どうしは分けない。
3. **後処理は、特性で選び、置き場所を決める。** テスト、レビュー、docsの同期、CI、着地のゲートなど、後処理はそれぞれ次の特性を持つ。
   - **守備範囲**：何を読み、どんな欠陥を、どの環境で捕まえるか
   - **費用**：結果までの時間と、占める資源（どの直列の資源を、どれだけ）
   - **確実さ**：偽の失敗（時々落ちる）があるか

   回すのは、変更と守備範囲が重なり、より安い後処理が捕まえない欠陥を捕まえるものだけ。それぞれを、最も安く捕まえられる段で1回回す。後処理に要るビルドも同じで、回す後処理を満たす最も安いもの（作り直さない、開発用、最適化、検査の軸）を選ぶ。1回ごとの固定費が大きい後処理（レビュー、CI、最適化ビルドなど）は、まとめて回して固定費を割る。まとめるのは、守備範囲が効く大きさ（レビューの目が届く差分）まで。
4. **止まりは、確実に届く知らせに変える。** 待ちは期限のあるコマンドにする。止まれば期限切れで終わり、終わりの知らせは必ず届く。途中経過の通知や、記録を見張るループには頼らない。
5. **計画は事実で組み替え、外れから学ぶ。** 見積もりは一覧の実測から引き、表にない数字は「推定」と書く。外れたら原因を追って、一覧かこの本文を直す。

## 2. 始める前

**規模を決める**（途中で変わってよい）：
- **調べないと分からない**：時間の枠を決めて、自分で調べる（目安30〜45分）。直す形が見えたら、もう一度規模を決める。
- **小**：1つの領域、担当なし、着地の前に重い後処理（CIなど）を待たない。会話に3行（作業、見込み、後処理と着地）を書いて進める。
- **大**：担当を出す、変更が2つ以上、または着地の前に重い後処理を待つ。以下を全部踏む。

**大の手順**：
1. 人の判断が要る点（仕様、userの感覚での確認、許可の要る操作）を先に聞く。計画が承認済みなら、計画は聞き直さない。
2. 作業に分け、作業ごとに資源・見積もり・依存を書く。docsなど同じ変更に入るべきものは、着地の前に入れる。
3. 後処理を選ぶ（原則3）。一覧の特性表から選び、それぞれを置く段（担当ごと、統合後、着地後）を決める。担当ごとに置くのは、変えた本人にしかできない最低限（単発の確認、テストの効き目、使う側の洗い出し）だけ。
4. 並列に分けるかを、直列案と並列案の完了時刻で決める（原則2）。分けるなら型を選ぶ。
   - **書くのは担当、確かめるのは親**：担当は調べて書き、本人にしかできない確認だけをする。重い後処理は親が統合後に1回回す。領域がはっきり分かれた作業に向く。
   - **担当が確かめて独立に着地**：無関係な変更を別々に着地させたいとき。資源の順番をずらす。
5. 工程表を`references/plan-template.md`で作業用の場所に作る。工程表は台帳を兼ね、会話が圧縮されてもここから戻せる。
6. 共有の準備（修正前のビルドなど）は1回だけ作って使い回す。待つのは、それが要る作業だけ。
7. 担当への指示は、全員`references/brief-template.md`から作る。言い回しの違いは、違う意味に取られる。

userが計画そのものを求めたとき、または仕様の判断を含むときは、計画を見せて確定を待つ。自動の催促（Stopフックなど）は承認ではない。

## 3. 実行中

- **見回り**：担当が長い処理を待つ間だけ、バックグラウンドの`sleep`（走っている作業の最短の見積もり、5〜15分）を1つ置き、起きたら台帳と実際の様子を見る（見方は一覧）。
- **棚卸し**：報告の前、会話の圧縮の後、担当が終わったときに、自分が起動した処理を一覧し、要らないものを止める。
- **担当の報告**：コミットと差分を確かめ、名前の挙がったテストを1つ回す。数値は条件の書いてあるものだけを使う。重い後処理を自分で回し直さない。

## 4. 組み替え

途中の事実が、見積もり・構造・判断の持ち主のどれかを変えたら、工程表を直し、記録を残す。

| きっかけ | 原則 |
|---|---|
| 遅れ（見積もりの1.5倍を超えた） | 実際に止めているもの（ロック、枠、人）を確かめる。止まりなら原因を直す。進んでいるなら見積もりと順番を直す |
| 構造の変化（範囲が広がった、変更どうしの依存や衝突が分かった） | 規模を決め直す。依存の順に1本に重ね、事前の検証も同じ順で重ねる |
| 新しい問題 | 同じ仕組みの2つ目なら、構造の作業として規模を決め直す。別の不具合なら、再現と一緒に記録して別の作業にする。userが決める設計の判断なら、選択肢を示して聞き、仕上がった部分は先に着地し、関係のない作業を進める |
| 後処理が落ちた | 落ちたものを手元で再現してから直す（推測で出し直さない）。時間切れだけなら負荷を疑って単独で回し直し、値の誤りや例外なら本物の不具合として直す。手元の安い後処理で捕まえられたものなら、次からはそれを前の段に置く |
| 外の変化（主ブランチが赤、userの新しい方針、会話の圧縮） | 主ブランチの赤は、診断より先に容疑を戻して緑にする。方針が変わったら、合わない作業を止めてから計画を作り直す。圧縮の後は工程表を読み直し、棚卸しする |

## 5. 着地

- 主ブランチ（masterなど）への統合を着地と呼ぶ。着地も事前の検証も、固定費の大きい後処理（原則3）。着地は、主ブランチに入っている必要が生じたとき（後続が依存する、ほかの人が使う、束が仕上がった、溜めすぎて切り分けにくくなる手前）に行う。事前の検証は、手元で見えない守備範囲に変更が触れ、主ブランチが赤になると困るときだけ出す。具体の基準とpushの決まりは一覧に従う。
- 事前の検証に出す変更は、同じころ着地するなら1本に重ねる（2〜3まで）。出す直前に主ブランチの先頭へrebaseし、着地が検証した木への早送りになるようにする。一部だけが緑なら、緑の部分から着地してよい。赤なら下の方だけを流して切り分ける。

## 6. 終わりと学び

- 工程表の予定と実績を比べ、外れた数字は次の着地のコミットで一覧を直す。worktreeと検証のブランチを消し、棚卸しする。
- 仕事ごとに、`references/log/<日付>-<主題>.md`へ記録を1件残す（小の仕事も、このスキルを使うべきだったのに使わなかった仕事も）。書くのは、規模、見積もりと実績、守備範囲の外で回した後処理、組み替えのきっかけ、userの指摘、スキルへの気づき。1件を1つのファイルにするのは、複数のマシンや人が同時に足しても衝突しないため。型が見えたら原則か一覧にまとめ、元の記録は消す。
- 完了が見積もりの1.5倍を超え、しかも30分以上遅れたら、原因を追ってこのスキルを育てる。スキルに従わなかった（見つからなかった、長すぎた、分かりにくかった）ための遅れも含む。小の仕事は、報告に原因と直すものを1〜2行書くだけ。大の仕事は：
  - 記録（ありかは一覧）から時間の行き先を測る。待ちは、止めていたものに付ける。
  - 根まで辿り、根の置き場所を直す：数字 → 一覧、手順 → この本文、決まり → その決まり（指示ファイルはuserに諮る）、道具 → 一覧に回避策を書いて修正を諮る、外の原因 → 記録だけ。
  - `references/cases/`に事例（内訳、根、直したところ）を残し、直した手順で事例をなぞって防げることを確かめ、userに報告する。原則を変える修正は、確定をもらってから入れる。
- 本文は肥大させない。足す前に、既存の原則で導けないかを考える。導けるなら、足すのは一覧か事例の側。
