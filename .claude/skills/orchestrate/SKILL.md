# 作業の段取り（資源とジョブのオーケストレーション）

目的は、与えられた問題を**正しく、エレガントに、安全に、そのうえでできる限り速く** 解くこと。速さのために前の3つは削らない。

**最初に、そのプロジェクトの資源と道具の一覧を読む。** culebraでは`references/project-culebra.md`。この本文はどのプロジェクトにも通じる原則と手順だけを書き、コマンド、容量、ロックの場所、CIの決まり、見積もりの数字は一覧の側に置く。一覧には今のmasterでできることだけを書き、道具が変わったら、その変更と同じコミットで一覧も直す。事例（原則の根拠）は`references/cases/`。

- **優先順位**：userのその場の指示 ＞ プロジェクトの決まり（CLAUDE.md、メモリ、一覧）＞ この本文の既定。たとえばuserが「worktreeの修正ごとに/simplify」と言えば、§2の「統合後に1回」より優先する。
- userが「判断はおすすめで進めて（大きな問題でない限り）」と言っているとき、「大きな問題」は次のどれか：userから見える仕様や振る舞いが変わる、戻せない操作（push、削除、公開）、頼まれた範囲を超えて作業が広がる、目的どうしの交換（速さとメモリなど）。これらは聞く。それ以外はおすすめで進め、選んだことを報告に書く。

## 1. 原則：完了までの時間は、直列の資源を通る作業の合計で決まる

担当を増やしても、この合計は縮まない。取り合い、待ち、衝突の解消の分だけ伸びる。直列の資源は、たいてい次の5つ。容量と、今どう調停されているか（されていないか）は、プロジェクトの一覧で確かめる。

| 直列の資源 | 典型 |
|---|---|
| 手元のマシンのコンパイル | メモリが先に尽きる。重いコンパイルは同時に1本が基本。ロックが一部しか守っていなければ、残りは自分で守る |
| CIの枠 | 同時に動かせるジョブ数の上限。とくに数の少ない枠（macOSなど） |
| 着地（共有ブランチへの統合） | 1本ずつ |
| userの判断 | userがいるときだけ進む |
| 自分（司令塔）の注意と文脈 | 1つだけ。会話が圧縮されると忘れる |

- **基本は直列。** 1本の流れで進め、直列の資源を空けず、重ねずに使う。
- **並列にするのは例外。** 1つの作業を細かく分けたとき、安全で、しかも完了が早まると見積もれた場合だけにする。コンパイルを使わない部分（調査、設計、コードとテストを書くこと、ビルドの要らない変更）は並べやすい。
- **後処理の守備範囲を見極める。** 効率を決める要の1つ。テスト、レビュー、CI、着地のゲートなどの後処理には、それぞれ守備範囲がある（何を読み、どんな種類の欠陥を、どの環境で捕まえられるか）。変更と守備範囲が重なる後処理だけを回す。守備範囲が重なる後処理どうしは、安い方で済ませる。重い後処理（全CIなど）は、軽いものでは捕まえられない残り（別のOS、ツールチェーン、長いスイープ）のためにだけ回す。守備範囲の外の変更に後処理を回すのは、時間と枠を使って何も確かめないことになる。各後処理の守備範囲は、プロジェクトの一覧に書く。
- **並列の見積もりには、後処理の増加分を入れる。** 分けた作業（サブタスク）ごとにテスト、レビュー、CIを回すと、検証が分けた数だけ増える。さらに取り合いで、完了がかえって大きく遅れる。どこまでをサブタスクごとに確かめるかは、計画で決める（§2の5）。

## 2. 始める前の計画

まず規模を見る。規模は途中で変わってよい（§4）。

- **調べないと分からない**（原因が不明、どこを直すか未定）：まず調査だけを、時間の枠を決めて行う（目安30〜45分）。自分で行い、担当は出さない。測る対象がメモリや速さなら、最適化したビルドが要る（コンパイルの1本に数え、7の修正前ビルドを使い回す）。直す形が見えたら、改めて小か大かを決める。
- **小**：1つの領域に収まり、担当を出さず、CIの事前検証（ci/ ブランチなど）も要らない。計画は会話に3行書くだけでよい（作業、見込み、着地のしかた）。工程表のファイルも見回りも要らない。使うのは、5の検証の層、§4〜§6と、§7の軽い道。
- **大**：担当を出す、変更が2つ以上ある、CIの事前検証を通す、のどれか。以下の手順を全部踏む。

大の手順：

1. **userの判断が要る点を先に集めて聞く。** 答えで作業の分け方が変わることがある。userが計画をすでに承認しているなら、計画は聞き直さない。聞くのは、仕様の選択、userの感覚での判断（音を聞く、見た目を見る）、userの許可が要る操作だけ。担当をuser待ちで止めない。
2. **作業に分ける。** 典型は、調査 → 修正と落ちるテスト → docs → 軽い確認 → レビュー → 重い確認 → CIの事前検証 → 着地 → 記録（メモリなど）。docsは着地の前に、同じ変更に入れる（docsもゲートで数えられることがある）。要らない段は書かない。
3. **作業ごとに、使う資源と見積もりと依存を書く。** 見積もりはプロジェクトの一覧の数字から引く。表にないものは「推定」と書く。検証の層は、その変更で問題を捕まえられるものだけを計画と見積もりに入れる（例：CIが読まないファイルだけの変更なら、CIの待ちは入れない。どのファイルが当たるかは一覧）。
4. **並列に分けるかを決める。** 直列の案と並列の案の両方で、完了時刻を見積もる。並列の案には、サブタスクごとの検証、コンパイルの順番待ち、統合（rebaseと衝突の解消）の時間を足す。並列の方がはっきり早いときだけ分ける。
   - **中心ヘッダ**（触ると大きな作り直しが起きるファイル。どれが当たるかは一覧）を触る作業どうしは、分けない。1本の流れにまとめ、依存の順に重ねる。
   - コンパイルは同時に1本（§1）。担当のビルド、自分の修正前ビルド、着地のビルドを、時間をずらして並べる。
5. **検証の深さを決める。** 検証には層がある。まず、変更と守備範囲（§1）が重なる層だけを選ぶ。選んだ層を、問題を最も安く捕まえられる段で1回だけ回す。各層の具体的なコマンドと守備範囲は一覧にある。

   | 層 | 置き場所の基本 |
   |---|---|
   | 単発の実行。新しいテストが修正前に落ちることの確認 | サブタスクごと（渡す前に要る最低限） |
   | 変えた振る舞い・形・名前を使う側の洗い出し。写しやまね（例の中の代用品、docsのコード）まで探す。見つかった場所を確かめる検査のうち、着地のゲートが回さないものは、CIの事前検証の前に回す | 変えた本人が、変更と同時に |
   | プロジェクトの速い検査（変更のたび、触った領域、docs、ゲートの数の上限、足したテスト時間の計測） | サブタスクごと、または統合後に1回 |
   | 自分で直接回すテスト（ゲートが回さない形のもの） | 変えた本人が |
   | レビュー（例：/simplify） | 統合後に、まとめた差分へ1回（userの指示があればそれに従う）。テストとdocsだけの変更には回さない |
   | 重い確認：全体のスイープ、最適化したビルドでの性能（時間とピークのメモリ。ホットパスのときだけ）、userの感覚での確認 | 統合後に1回 |
   | CIの事前検証（全CI） | 統合後に1回（§5の決まりで要るときだけ） |
   | 着地（そのゲート） | 着地のたびに1回 |

   - **確率的に落ちるテスト**（競合、負荷の下でだけ出るもの）は、「修正前に落ちる」を統計で確かめる。負荷をかけてN回回し、修正前後の失敗数を比べる。Nは、修正前に5回ほど落ちる回数にする（失敗の率がpならN ≈ 5/p。20回に1回なら約100回）。Nと負荷の作り方は記録する。実機の装置やファイル監視を使うテストは、サンドボックスの外で回す。
   - **ビルド時の定数でしか落ちることを示せないテスト**は、手元のビルドで定数を一時的に変えて確かめ、その変更は捨てる。実行時に変えられるようにする（つまみを足す）のは仕様の判断なので、userに聞く。
   - 代表的な型は2つ。どちらにするかは仕事ごとに、上の見積もりで選ぶ。
     - **書くのは担当、確かめるのは親**：担当は調査とコードやテストを書くことだけを行う（ビルドしない、または単発の確認だけ）。テスト、レビュー、CIのような重い処理は、親（司令塔）が統合した結果に1回だけ回す。コンパイルが取り合わず、検証も増えない。領域がはっきり分かれていて、統合で衝突しない作業に向く。
     - **担当が自分で確かめて独立に着地**：互いに関係のない変更を、それぞれ別に着地させたいときに使う。担当ごとに上の層を回すので、コンパイルは時間をずらし、CIは §5の本数の範囲に収める。
   - 決めた深さは、担当への指示の「Checks for this subtask」に書く。
6. **工程表を作る。** `references/plan-template.md`の形で、作業用の場所（scratchpadなど）に置く。工程表は、自分が起きるたびに読み直す台帳を兼ねる。会話が圧縮されても、ここから戻せる。
7. **共有の準備をする。** 修正前の最適化ビルドが要るなら、同じコミットのものがあれば使い回す。なければ1回だけ作り（場所と作り方は一覧）、パスを全員に渡す。これを待つのは、修正前のバイナリが要る作業だけでよい（読むことと書くことは先に始めてよい）。
8. **担当への指示は、全員`references/brief-template.md`から作る。** プロジェクトの一覧にある「担当に渡す決まり」をそのまま貼る。担当ごとに書き方を変えない。言い回しの違いは、担当によって違う意味に取られる。

計画をuserに見せるのは、userが計画そのものを求めたとき、または仕様の判断を含むとき。そのときは確定の返事を待ってから実行に移る。自動の催促（Stopフック、ゴールの確認）は承認ではない。

## 3. 実行中

### 待ち方
実測では、バックグラウンドのコマンドが終わったという知らせは、必ず司令塔を起こした。サブエージェントの途中経過の通知は、しばしば起こさなかった（数字は`references/cases/`）。だから、止まりが「コマンドの終わり」として届く形にする。

- **待ちは、期限のあるコマンドにする。** 待ちのループを自分で書かない。作業記録やログを`grep`で見張らない（書式が違えば永久に回る）。待ちが待ちを待つ形も作らない。
- **見回り**（大のとき、ビルドや長い処理を待つ担当がいる間だけ）：見回りが残っていなければ、`sleep <走っている作業の見積もりのうち短い方。5〜15分>`をバックグラウンドで1つ置き、そのtask idを台帳に書く。起きたら、台帳を読み、実際の様子（ロックの持ち主、プロセス、CI。確かめ方は一覧）を確かめる。
- **CIを待つ**：期限付きのコマンドで待つ（例は一覧）。
- **棚卸し**：報告の前、会話が圧縮された後、担当が終わったときに、自分が起動したバックグラウンドの処理を一覧する。要らないものは`TaskStop`で止める。

### 担当の報告を受けたら
- コミットのSHAと`git diff --stat`を確かめる。
- 名前の挙がったテストを1つ、担当のバイナリで回す。
- 数値の主張は、条件（ビルド、入力、回数）が書いてあるものだけを使う。
- 重いゲートを自分で回し直さない。それはCIと着地の仕事。

## 4. 組み替え

途中で分かる事実は計画を変える。きっかけが来たら、工程表の見積もりと順番を直し、組み替えの記録を残す。

| きっかけ | 対処 |
|---|---|
| 作業が見積もりの1.5倍を超えた | 実際のプロセスと、ロックの持ち主を確かめる（§3）。止まっていれば原因を直す。進んでいれば見積もりを直し、後ろの作業の順番を見直す |
| 調べて直す形が見えた、または作業が増えた | 規模を決め直す（§2）。大になったら、ここから工程表を作る |
| 2つの変更が同じファイルで衝突する、または片方が他方を前提にする | 依存の順に重ねる（後の担当に、前の担当のブランチの上へ載せ直させる）。CIの事前検証も同じ順で1本に重ねる |
| 本筋と別の不具合が見つかった | 再現手順と一緒に記録する。止められている場合を除き、そのブランチでは直さない。直す前に最新のmasterで、もう直っていないかを見る。ただし、同じ仕組みが働く2つ目の問題なら、全部の箇所を洗い出して構造で直す（範囲が広がるならuserに諮る） |
| 途中で、userが決めるべき設計の判断が出た | 選択肢と根拠をまとめてuserに聞く。答えを待つ間は、その判断に関係しない作業を進める。すでに仕上がった変更は先に着地し、判断待ちの部分は別の作業として切り出す |
| テストが時々落ちる | 落ち方で分ける。時間の上限を超えただけ（タイムアウト）なら、その検査を単独で回し直し、通れば負荷による偽の失敗として記録し、構造の直しは別のタスクにする。値の誤りや例外なら、負荷で表に出た本物の競合として、再現して直す。その時々落ちること自体が仕事なら、それが本筋 |
| 自分のCIの事前検証が赤 | 落ちたジョブを手元で再現してから直す（推測でpushし直さない）。直したら、同じブランチにpushし直す。手元で先に捕まえられた検査なら、次からは事前検証の前の層に入れる |
| 着地が自分の変更で落ちた（例：ゲートの数の上限） | 落ちた検査を手元で回して直し、同じ変更に入れて着地し直す。次からは、その検査を事前検証の前の層に入れる |
| 重ねた事前検証のうち一部だけが緑、残りはまだ | 緑の部分から順に着地してよい。残りはmasterにrebaseしてから、別のrunで検証する |
| 測定で性能やメモリの後退が見つかった | 直して測り直す作業を、工程表に足す。指標どうしの交換（速いがメモリが増える）が残るなら、userが決める |
| masterが赤になった | 診断より先に、容疑のコミットをrevertして緑に戻す |
| userの新しい方針 | 走っている作業のうち、方針に合わないものを止めてから、計画を作り直す |
| 会話が圧縮された | 工程表を読み直し、バックグラウンドの処理を棚卸しする |

## 5. 着地とCI

- 主ブランチ（masterなど）への統合を「着地」と呼ぶ。
- CIの事前検証を通すかどうかは、プロジェクトの決まり（一覧）に従う。通さない変更は、着地してpushする。
- 変更がCIの読まないファイルだけなら、pushした後のCIの結果も待たない（どのファイルが当たるかは一覧）。
- 事前検証を通す変更は、互いに依存していなくても、同じころに着地するなら1本に重ねる（2〜3まで）。本数を減らすほど、CIの枠とキャッシュを守れる。
- 同時に流すrunは、CIの枠に収まる本数まで（目安は一覧）。pushの前に、ほかのセッションのrunも含めて走っているものを見る。
- 事前検証に出す直前に、masterの先頭へrebaseする。着地が、検証したのと同じ木への早送りになる。
- 赤が出たら、下の方の変更だけを流して切り分ける。
- pushはプロジェクトの決まり（着地ごと、または検証済みの束ごと）に従う。pushの前に、自分の分以外のコミットが混ざっていないかを見る。

## 6. 終わり
- 工程表の予定と実績を比べる。外れが大きかった数字は、次の着地のコミットで一覧を直す（一覧が数字の置き場所をほかのファイルに指していれば、そちらを直す）。完了が見積もりの1.5倍を超え、しかも30分以上遅れたなら§7へ。
- worktreeとCIのブランチを消し、バックグラウンドの処理を棚卸しする。
- メモリの該当する項目を更新する。

## 7. 見積もりより大きく遅れたら、原因を追ってこのスキルを直す

このスキルに従っても、完了が見積もりの1.5倍を超え、しかも30分以上遅れたときは、終わった後に必ず振り返る。このスキル自体を育てる仕組みはこれだけなので、省かない。スキルに従わなかった（見つけられなかった、長すぎた、分かりにくかった）ために遅れたときも、同じくスキルの穴として扱う。

- **軽い道**（小の仕事）：報告に「何が遅れの原因で、何を直すか」を1〜2行書き、直すものは次の着地のコミットに入れる。事例のファイルは作らない。
- **全部の道**（大の仕事）：
  1. **時間の行き先を測る。** 自分と担当の記録（ありかは一覧）から、時間を「考える・書く」「ビルド」「テスト」「レビュー」「CI」「待ち」「やり直し」に分ける。待ち時間は、実際に止めていたもの（ロックの持ち主、CIの枠、user）に付け、直前に起動した処理のせいにしない。数字は記憶ではなく記録から取る。
  2. **根を探す。** 症状（例：ビルドが遅い）で止めず、なぜそうなったか（例：ロックを二重に取った、なぜ二重に取ったか）を辿る。同じ根から出た症状は1つにまとめる。
  3. **直す場所を決める。**
     | 根の種類 | 直す場所 |
     |---|---|
     | 見積もりの数字が外れた | プロジェクトの一覧（または数字の置き場所） |
     | 手順や判断の穴（このスキルが導かなかった、誤った方向に導いた、従われなかった） | この本文 |
     | プロジェクトの決まり（CLAUDE.md、メモリ）の穴や食い違い | その決まりの側。CLAUDE.mdの変更はuserに諮る |
     | プロジェクトの道具の穴 | 一覧に今の回避策を書き、道具の修正は別の作業としてuserに諮る |
     | 外の原因（CIの障害など） | 事例に記録するだけ |
  4. **事例を残す。** `references/cases/<日付>-<主題>.md`に、内訳の表、根、直したところ（スキルのどの節か）を短く書く。次の判断の根拠になる。
  5. **直したスキルを確かめる。** 修正した手順で、その事例を最初からなぞり、遅れの原因が防げることを確かめる。大きな修正なら、何も知らない担当に事例を渡して計画させ、結果を実際と比べる。
  6. **userに報告する。** 何が遅れの原因で、スキルのどこをどう直したか。手順の大きな変更（原則や規模の決め方を変えるもの）は、確定の返事をもらってから入れる。直したものは次の着地のコミットに入れる。
