# 2026-11-13 Synth P15: 利用者の処理のネイティブ化（評価、ループの道、round と latch、ランプをまとめる）

- 規模: 中（エンジン・bindings・前処理・テスト・docs）。評価の試作 → 計画 → 独立レビュー1回（10件すべて採用） → user の /goal「レビューしてから実装へ、判断はお奨めで」 → P15a（ループの道）→ P15b（round、latch、信号の hz/db）→ P15c（ランプをまとめる）の順に実装、/simplify は束ねた差分に1回（品質6、再利用4を採用、効率1は層の分離を崩すので見送り）。ci/ は使わず、着地のあと push して CI を見た。
- 見込みと実績: 見込みは約5時間（dev 4回）。実績は dev 6回（変異の確かめに1回、/simplify の後に2回）。
- 評価で分かったこと: ループのない利用者の処理（3次の歪みなど）は組み込みの部品と同じ速さ（-O3 で部品1つ 1 ns 未満〜数 ns）。ループ（feedback）の中は部品1つ1サンプル 18〜25 ns と重く、Graph::work が128サンプル分の作業用の配列と for を1サンプルにも使っていたのが原因。サンプル数を、ループの段では型引数から決まる定数1にしただけで 7〜9 ns に（一極フィルタを組んだもの 72.8 → 26.9 ns、ベンチのループのグラフ 0.60〜0.78 倍、全グラフ同標本）。値の予定をブロックの頭でまとめて求める案は速くならず捨てた。JIT の関数を呼ぶ道は取らない（全レーン対称に反する、例外と寿命が未解決、上の費用で足りる）。
- 書けるかの表: 一極、DC 除去、3次の歪み、スロープリミッタ、折り返し、包絡の追従は今の部品で書け、定義との差は 0 か 1e-16（VM と JIT で同じ）。書けなかった量子化、サンプル＆ホールド、半音の揺れを round、latch、信号の hz/db で埋めた。割り算・log・比較は見送り（付録D）。
- 組み替えのきっかけ: (1) latch のテストの参照を「2000 サンプルごと」と決め打ちにしたら、impulse は位相の足し算の誤差で 2001 サンプル目に発火していた。参照はトリガーの標本から作る形にした。(2) /simplify の後の gc-stress の手当て（新しい区切りをブロックに）で synth_sources は 17.3 → 15.8 CPU 秒。(3) segment を配列を返す形（map）にすると組み立てが 64 → 68 µs（VM）。+= を extend に変えても同じで、map のクロージャと小さな配列の分。ガイドの勧める形を残した。
- 測ったこと: ランプをまとめると Voices の1ノートの組み立てが VM 82 → 68 µs、JIT 37 → 33 µs、標本は VM・JIT とも前後でバイト一致（216089 行）。テストの JIT CPU: graph_sources 4.0 → 4.7、synth_sources 3.8 → 4.8 秒。gc-stress の3つの実行: 10 → 12、10 → 16 CPU 秒。
- テストの効き目: エンジンの変異3つ（round の半分の切り上げ、latch の水準トリガー、latch の初期の状態）を環境変数で切り替える1つのビルドで、新しい確認9つを1つずつ回し、どれも対応する変異で落ちることを確かめた（MUT=0 で全部通る）。
- 気づき: 変異をビルドごとに分けず、実行時の環境変数で切り替えると、エンジンの変異はビルド1回で済む。テストの最初に落ちた確認が後ろを隠すので、確認ごとに独立に回す小さな検査（probe.cul）を書くのが速い。
