# B6: 組み込みのイテレータの has_next / next を remove して設定し直すと速い道が型を取り違える

- 規模：大（CI を待つ）。仕様は user 選択（差し替えたものを使う）→ 計画 v3 → レビュー1回 → user 確定 → 実装3コミット → /simplify → ci/iter-next-replace と asan.yml の手動起動 → 着地。
- 構造：速い道の正規の組（step と2つの中継関数）を `JitIterFastOps` の1か所に置き、ラッパーを作るときも照合するときも同じ組から取る。照合（`_iter_fast_walks`）は速い道に入る直前に毎歩、ジェネレータの `_jit_gen_walks` と同じ規則。
- 性能（`just build`、命令数。壁時計は別セッションのビルドで揺れた）：1歩あたり約18命令、空の for-in で +6%、map.filter.map は VM +3%・JIT +6%。照合を歩き始めの1回にする案（ABI 変更が約25か所）は user と相談して見送り。
- テスト時間：test_iter.cul の `--jit` が 0.50→0.95秒（VM は 0.03秒のまま）。JIT が1操作ごとに出す IR が大きい（`iter().take(4).collect()` 1行で約800行）ためで、書き直し3通り（共有クロージャ、関数に包む、表の形）はどれも縮まなかった。
- 組み替えのきっかけ：
  - /simplify の品質レビューが gc-hazard の自己テストの古い型を見つけた（そのままだと CI の gc-hazard が落ちた）。
  - 先読みのセルを読むアクセサ関数を作ると、gc-hazard ツールが借りた読みを見失い ALLOWED の行が「見つからない」で落ちた。直接の `captures[...]` に戻した。
  - 修正前に通っていた2つの確認（守りの assert）は効き目がないので消した。残る9つは1つずつ修正前に落ちる（3つは SIGSEGV）。
- スキルへの気づき：テストを足したら IR の行数（`--emit-llvm`）も測る。JIT のテスト時間は行数でも assert 数でもなく IR の大きさで決まる。
