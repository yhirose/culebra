# 右側の演算子メソッド（`__rsub__` 等）

- 規模: 大（ci/ を待つ）。直列、担当なし。/simplify の3人だけ並列。着地 2d28b75c（ci/ で全28ジョブ緑、そのまま早送り）。
- 見込みと実績: 見込み3〜3.5時間（CI 35分を含む）。実績はおおむね見込みどおり。dev の作り直しは4回（修正前、変更、変異、戻し）。中心ヘッダなので1回約5分。
- 計画で効いたこと: 数が左の演算が executor・JIT・`@value`・Synth の部品のどれも `_dispatch_arith_special` の1か所を通ることを、計画の段で小さな例で確かめた。直すのは1か所で済み、範囲が広がらなかった。
- 組み替えのきっかけ: user が決めた「右側の overload が合わなければ DispatchError」は、確かめると今の左側の決まり（型注釈が1つなら引数の TypeError、overload が2つ以上なら DispatchError）と違った。選んだ案の説明「左と同じ決まり」の方に合わせ、user に報告した。
- 守備範囲の外で回したもの: 変異のビルド1回。変わらない振る舞いを押さえる assert（直す前でも通るもの）が効くかを確かめるため、順番を入れ替える変異と反転を広げる変異を同時に入れ、5つが落ちることを確かめた。
- 落ちた検査: `check-generated` の spec-examples（仕様の節に実行できる例が要る）と、docs のブロック数の上限。どちらも `just check` は回さず、着地のゲートが回す。一覧（§5）の「着地の前に check-generated」のとおりで、そこで捕まえた。
- /simplify の指摘で入れたもの: コメントと docs の文面（TypeError の場合、右の値が答える段、自分のメソッドに回さない演算子は5つ）、テストのイディオム（`assert_throws` の戻り値、`||` のラムダ、欄の引数）。
- スキルへの気づき: 直す前でも通る assert は「テストの効き目」では確かめられない。変異を同時に複数入れれば、ビルド1回で済む（互いに打ち消さない組み合わせを選ぶ）。
