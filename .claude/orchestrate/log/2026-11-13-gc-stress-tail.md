# 2026-11-13 ci-gc の gc-stress の段の短縮（別セッションの申し送り）

- 規模: 調べないと分からない → 小（justfile の1関数とテスト1本、着地の前に重い後処理を待たない）。調査 → 計画 → 独立レビュー1回 → 実装 → /simplify → 着地。
- 見込みと実績: 調査の枠 45 分に対して約 50 分。実装と確認は約 1 時間（段の比較の 2 往復が 25 分）。
- 調べ方: 全 360 ファイルの gc-stress の3つの実行の CPU 秒を、JIT のキャッシュを温めてから測り（8並列、数分）、その数字で xargs -P4 の先着配りを再現した（scratchpad の gc/schedule.py）。段は下限（合計÷4）の 1.25 倍で、test_synth_voices が最後に1本だけ走る尻尾だった。区切りごとの refs-vm の CPU を前置きの写しで測り、70 回の play の区切りが 28 秒のうち 20 秒で、前の区切りの標本が生きているためだと分かった（単独 1.4 秒、生きていると 13.2 秒）。
- 計画のレビューで分かったこと: CI の段の時間はランナーの CPU の機種で 2.6 倍違う（EPYC 7763 で 630 秒前後、9V45 で 240 秒前後）。申し送りの「600 秒台」は大半がこれで、CI の前後の比較は機種ごとに並べる。テスト側の直し（B）が主で、割り当て（A）の上乗せは数 %。
- 直したもの: B はテストの区切りの標本をブロックに閉じ込める（3つの実行で 74.8 → 18.3 CPU 秒）。A は gc-stress のタスクを実行ごとにし、1周目に全ファイルの conservative の --jit、2周目にファイルごとの refs-vm と refs-jit（refs-jit は自分の jit がコンパイルしたものをリンクする。並べ方は /simplify の効率の指摘で、JOBS が多い手元の尻尾も縮む）。段は JOBS=4 の手元で 156/155 → 152/148/154 秒。
- 見送り: GC が数だけの配列の要素をたどらないようにする案（配列への書き込みの全経路に印を保つ必要があり、gc-stress のためだけには釣り合わない）。test_kauai の区切りの整理（後ろほど重くなる形、合計の数 %）。
