# ブラウザの FM Synth でキーが約6秒遅れて鳴る

- 規模: 中（ci/ を待つ）。直列、担当なし。着地 50e37bc9（ci/ で全ジョブ緑、そのまま早送り）。
- 見込みと実績: 原因の特定に約30分、修正と確認に約1時間。dev のビルド2回、wasm 2回。
- 計画で効いたこと: 推測で直さず、まず node で worker を動かして測った。キーからミキサー宛ての命令までは 1 ms 以内と分かり、遅れはミキサー側にあると絞れた。最初の見立て（AudioContext が最初の操作で作られる）は入口としては合っていたが、それだけでは6秒にならない。グラフの時計の数え方の食い違いまで読んで、ようやく説明がついた。
- 組み替えのきっかけ: 直す方針は案を3つ出して user が A を選んだ（遅れて描き始めるグラフの時計を、その遅れの分だけ進めて始める）。A では mixer_test の既存の確認（台が毎回ミキサーを遅れて作る）が落ちた。その確認は「間に合うミキサー」の場面として、壁時計を止めて確かめる形に変えた。
- 守備範囲の外で回したもの: なし。音まわりのテストを CULEBRA_AUDIO=on のまま回し、デバイスがある状態で test_synth_play が落ちた。ゲートと同じ off で回し直して緑。
- 落ちた検査: 新しい2つ（audio_engine_test、mixer_test.mjs）が修正前に落ちることを確かめた。
- スキルへの気づき: 試験の台が本番とタイミングの前提を違えている（ミキサーをいつも遅れて作る）と、その台の既存の確認が、修正で変わる振る舞いを暗に固定していることがある。修正で落ちた既存の確認は、壊したのか前提が違うのかを分けて扱う。
