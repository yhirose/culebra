# 長い関数の JIT の IR を小さくする（flight-in-ny #21）

- 規模：大（計測が主、CI を待つ）。見込み約10時間、実績は着地まで約11時間（夜通し、負荷とメモリ不足でビルドが延びた分を含む）。
- 着地したもの：①集計の道具（CULEBRA_JIT_BLOCK_STATS）②PropVal の形（runtime に prop_value、executor と共有）③レビューで見つかった既存の executor/JIT の食い違い（Object の `.name` など、投げる getter のリーク）。fdm の Model.step 13,497→12,662 ブロック、読み込み 3.3→2.9 秒、最適化しない1ステップ 8.3/15.0→6.7/13.6µs。
- 保留にしたもの：片付けパッドの解放から判定を外す（ブロックとコンパイル時間は大きく減るが、レジスタ割り当てが変わって value_physics の scalars +43%）。3段版は jit-ir-shrink-3stage に残した。着地後に解決案を試験で比べた（第2・3段の上で）：線を超える関数だけ判定を外すと、value_physics は変わらず、fdm の読み込み（optimize+codegen）2.79→2.63秒。全関数で外す・値の選択にする案は、最適化する関数まで縮んで線の下に落ちる関数が出て、読み込みがかえって延びた（3.12秒、3.39秒）。
- 計測の道具立て：試験の切り替えを環境変数で1つのバイナリに入れ（CULEBRA_EXP_*）、1回のビルドで多くの組み合わせを測った。切り替えはコミット前に master の版から入れ直して消した。
- 採らなかった形（数字は docs/_history.md 17、#21）：四則演算の選択形、着地点の switch 共有、invoke の続きを畳む、ReleaseMany の一本化。どれも「ブロックは減るが速い経路か最適化後が悪い」。
- 組み替えのきっかけ：
  - 最適化したときの重さの正体（着地点が slot の SSA を読む → 入口の多い phi）は、上限を測る切り替え（パッドを空にする、リーク前提）で分かった。根本の手（slot の写しをメモリに持つ、型の特化）は user の判断に回した。
  - IR が縮むと 4096 の線の下に落ちる関数が出て、起動が延びる。線は変えず、事実として報告した。
  - メモリ不足でハーネスがビルドを止めた（ほかのセッションのビルドと重なり）。以後 CULEBRA_BUILD_JOBS=1〜2 で回した。
  - /simplify が第2段で遅い経路の呼び出し2回と op 位置の公開条件のずれを見つけ、runtime の関数1つにまとめ直した。大きな直しなので再レビューを1回 → 既存の食い違いが見つかり、別コミットで直した。
  - 着地直前のベンチの取り直しで、第1段だけの組み合わせを一度も測っていなかったことに気づき、value_physics の退行が見つかった。user と相談して第1段を外した。
- 後処理：just check、phase run_diff_vm_jit（374本）、vm_cases、doctest、check-generated、変異ビルドでの確認の効き目、release ビルドで交互・最小値のベンチ（fdm、tests/perf、tools/bench の ops・value_physics・vector_loop）、ci/ 3回（第1段のみ／3段／2・3段）。
- スキルへの気づき：
  - 計測は「静かな時間に、条件を交互に N 周して最小値」でないと使えない（load 8〜18 の時間帯は1ns 単位の行が数割揺れた）。
  - 段を重ねて測るときは、各段を単独でも同じベンチ一式に通す。重ねた組み合わせでしか測っていないと、ある段の退行が別の段の改善に隠れる（ここでは一本化が value_physics の退行を偶然打ち消していた）。
  - asan.yml の手動起動は、そのワークフローが GitHub の既定ブランチに push されるまで使えない（ローカルの master にだけある間は 404）。
