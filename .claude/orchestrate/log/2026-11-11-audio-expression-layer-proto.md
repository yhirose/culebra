# 2026-11-11 Audio の「式の層」の試作(着地は記録のみ)

- 見込み: ビルド1回(ccache で短い)と、Culebra のスクリプト約250行、測定。実際: ビルドは短く、試作とその直しで、構文の誤りの直しが5回あった(下記)。
- 内容: `Part` を値のクラスとして組み立て、`build`(id の表で、同じ値を1つの部品に共有)と `render` で `Audio.Graph` に変換する約120行の試作。手書きの Graph と、連鎖、トレモロ(式を値に)、FM(`phase:`)、エコー(UFCS で `.echo()`、同じ式を3回使う)、`[a, b].mix(0.5)`(配列への UFCS)を、サンプル単位で比べた。`culebra` と `--jit` の両方で、差 0.0。
- 分かったこと: (1) `Part` を Culebra のクラスにすれば、演算子の多重定義も UFCS も、そのまま使える。ネイティブの部品への多重定義は不要。(2) `+`、`*` は、数が左でも自動反射する(`docs/language.md` の Auto-reflection)。`-` と `/` は反射せず TypeError。最初、私は「左の項だけ」と読み違えた。(3) いまの Shadow prohibition は、外側の関数の変数が対象で、モジュール最上位の同名は隠すだけ。ワイルドカード取り込みで衝突をエラーにするなら、規則の拡張が要る。(4) コストは、組み立てあたり約25 µs の増加。
- 私のコードの誤り(試作中): キーワード専用引数は `*` の後に `q = 0.707`(`q: 0.707` は型注釈で構文エラー)、スライス `[a : b]` はない、変更できるプロパティは `{mut n: 0}`、欠けたキーの `obj[key]` は KeyError、`type_of(インスタンス)` はクラス名を返す(これで、最初の実行は2つの試験が不一致になった)。
- 教訓: ドキュメントの「Operator overloading」の節だけで判断せず、同じ章の「Auto-reflection」まで読む。試作のスクリプトは、小さく書いて、構文と型の判定の誤りを先に潰す。
- 見落とし: `Env` のカーブ、`feedback`、`Voices`、`play` の自然な終わりは、試作に入れていない。デバイスがなく、再生は確かめていない。
- 後処理: 着地は記録のみ。試作のコードは、リポジトリに入れていない(scratchpad)。
