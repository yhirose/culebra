# 開発の流れの改善（変更の範囲、サンドボックスの作り直し、穴ふさぎ）

- 規模：大。担当1人（サンドボックスの作り直しの調査と修正。コンパイルを使う作業はこれだけ）と、自分（justfile、ci.yml、シェルの変更。コンパイルを使わない）を並列にした。同じjustfileとci.ymlを触る作業は自分が1本で書いた。
- 見積もりと実績：
  - 計画の見積もりは約3時間（CI 35分を含む）。
  - 実績の時間は、工程表の「実績」欄をその場で書かなかったので、正確に測れていない。反省：作業の終わりごとに、時刻を工程表に書く。
  - CIは単独の1本で、約22分（ci/ブランチ、27ジョブ）だった。35分は、複数のrunが重なったときの値だった。
- 後処理の置き方：
  - /simplifyは束全体に1回（レビュアー3人）。
  - 手元のtest-devは2回（1回目は`midi_test`が負荷で落ち、直して2回目で通った）。
  - ci/ブランチは1本。ci.ymlを直して出し直したので、最初のrunを約4分で取り消した。
  - 着地とpushは1回。
- 守備範囲の外で回した後処理：なし。着地のゲートは、変更がfullなので回した。
- 組み替えのきっかけ：
  - レビューで、lightの範囲に漏れ（Kauaiのaot、wrap、MNISTのフォント）、名前を変えたファイルの数え漏れ、ci/ブランチの取り消しと判定の食い違いが見つかった。実害につながる穴だった。
  - 着地のゲートの`doctest`は、約7秒の見込みが、JITのキャッシュがなく20秒以上だった。共有のキャッシュを使うようにした。
  - 途中で、userが「masterのCIは省ける」と決めた。ci/ブランチを出し直して、`verified`の判定を入れた。
- userの指摘：なし（この束の作業中）。
- スキルへの気づき：
  - 原則3（守備範囲で後処理を選ぶ）の延長として、着地とCIの範囲を絞る道具（変更の範囲の表）が効いた。表を1つにして、CIの側の写しは検査で縛る形がうまくいった。
  - 担当が見つけたサンドボックスの原因（`sysctl`が拒否され、CMakeの既定のアーキテクチャが変わる）は、記録の中で78回、約130分/週の最大の損失だった。調べる担当を出す前に、ログから原因を絞れていれば、さらに早かったかもしれない。
  - 工程表の実績欄を書かないと、スキルの§6の予定と実績の比較ができない。
- 反映：
  - `tools/checks/change_scopes.txt`、`misc/change_scope.sh`、`misc/land.sh`、ci.ymlの`scope`ジョブと`verified`、CMakeLists.txtの先頭、`misc/gate_jit_cache.sh`。
  - 一覧：変更の種類から引く表、CIとビルドの実測の数字、「ci/で緑だったコミットはmasterで回し直さない」。
- 検証：着地したmasterのCIは`scope`ジョブが`verified`と判定し、ほかの26ジョブを省いた。runは成功。
