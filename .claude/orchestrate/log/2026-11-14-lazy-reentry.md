# 2026-11-14 遅延の連鎖の再入を ValueError に（小①）

- 規模: 小（規則1つ、iter.inc.h の一歩を囲む RAII と leaf の分け方）。user の決定: `ValueError: iterator already running`、標準ライブラリが作る iterator すべて、位置は再入した呼び出し。
- 見込みと実績: 見込みは半日。実績は半日強。計画の独立レビュー1回（tail-resumptive な handler の節という見落とした再入の道、印は bit ではなく4つ目の状態、前の値を戻さない）。
- 組み替えのきっかけ: (1) リリースビルドで交互に測ると `--jit` で +17〜23%。プロファイル（`sample`）で `_tlv_get_addr` が増えていた。投げる所で呼び出し位置（thread_local）を読んでいたのを、コンパイラが毎回の道に出していた。冷たい関数に分けて +1〜2% に。leaf（利用者のコードを走らせない元の iterator）を印なしにしたのは構造上の理由で、こちらは効き目が小さかった。(2) /simplify の品質の観点が、Object のキーの iterator は非 String のキーで `eq`（利用者のコード）を走らせるので leaf ではないと見つけた。印ありに移した。
- 気づき: 性能の遅れは推測で手を足さず、プロファイルの差（どの関数のサンプルが増えたか）で原因を特定すると一手で済む。thread_local の読み込みは、投げる道に置いても毎回の道に出されうる。冷たい関数（`[[noreturn, gnu::noinline, gnu::cold]]`）に分けるのが repo の流儀。
