# Playground の最初の1音が遅れる（ミキサーをページを開いた時点で作る）

- 規模: 中（ci/ を待つ）。直列、担当はレビューの3人だけ。
- 見込みと実績: 前提の確認（suspended の AudioContext で worklet の port に届くか）に約15分、テストを先に書いて落ちるのを見るまで約30分、実装と変異の確認に約30分、/simplify に約20分。wasm のビルド3回（各約3分）、dev 2回。
- 計画で効いたこと: 未確認の前提を最初に潰した。Chrome の拡張がつながらなかったので、ヘッドレス Chrome（`--autoplay-policy=document-user-activation-required`、sandbox の外）で試験ページを開き、コンソールの出力で確かめた。suspended でも addModule、processor の生成、port と MessageChannel の往復は届き、process だけが呼ばれない。
- 組み替えのきっかけ: 決まり（位置を壁時計に追いつかせる）を Engine の各部に当てはめると、曲（スケジュール）は位置が飛ぶと過ぎた音符がまとめて鳴る（スリープ明けならループが何時間分も回る）と分かった。基準点も、確定案の「最後のリセットから」では機器と Date.now の時計のずれが積み重なる。この2点を user に聞き、推奨（曲は hold、基準点は直前の描画）に決まった。/simplify の品質の担当が、1回に描く量の大きい機器では描画のたびに追いつきが働く懸念を出したので、閾値を 100 ms から 250 ms に上げ、4096 フレームの burst のテストを足した。
- 守備範囲の外で回したもの: なし。`just check` の test_fs_watch は sandbox が FSEvents を拒むので、sandbox の外で回した（既知）。
- 落ちた検査: 新しい確認は、直す前のコードで落ちるか、規則の変異（7つ）のどれかで落ちることを確かめた。
- スキルへの気づき: 「位置を進める」のような時間の飛びは、時間で動く部品ごと（待っている音、グラフ、曲、鳴っている音）に意味が違う。決まりを1つにしても、部品ごとの当てはめは仕様の選択になるので、実装の前に洗い出して聞く。
