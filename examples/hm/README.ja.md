# hm — linzの隣にもう一つ、Algorithm W

この例は、一つの問いに答えるために作った。`examples/linz/lin.cul`
（型検査器——ソースにすでに書かれている型を確認するだけの仕事）の
`typing.cul`の形は、別の形の言語に対しても使い回せる「型システムの
道具箱」に一般化できるのか？ `hm.cul`は逆に、型を**何もないところから
推論する**——Hindley-Milner推論（Algorithm W）を、型注釈が一つもない
小さな`Int`/`Bool`/`if`/`fn`/関数適用/`let`の言語に対して行う。あえて
「単一化」と「代入」という、linzには存在しない部分に負荷がかかる題材を
選んだ。

## 実際に移植できたもの

- **文法の書き方。** `%whitespace` + `%word` + `IDENT`内の`RESERVED`
  除外という3点セットは両ファイルで同じで、変わるのはキーワードの
  リストだけだった。これは`Peg`の知見であって型システムの知見では
  ない——キーワードを持つDSLなら型の有無に関わらず使い回せる。
- **`fail(node, msg)` → `throw {kind, message, line, column}`。**
  （`pl0.cul`に続き）3つ目の実装で同じ形になった。「`Peg`駆動のツールの
  エラーはこう書く」という流儀としては価値があるが、`kind`の文字列が
  言語ごとに違うことこそが各ドライバでの見分けを可能にしているので、
  ファイル間で共有する関数にする意味はない。
- **`bound(env, name, value)`。** `Object`リテラルには計算キーの構文が
  なく、ここでのすべての束縛がソースから読んだ名前——コンパイル時には
  分からないキー——である以上必要になる、コピーしてから添字で1件だけ
  書き換えるだけの3行。今回`%word`と計算キーを巡る会話から生まれたこの例で、
  2つの独立した実装に**全く同じ形**で必要になったことから、実在する
  頻出パターンだとは確認できた。ただし3行では、標準ライブラリの関数に
  する方が自分で書くより高くつく。
- **ドライバ。** `import`し、`Sys.argv`から`--ast`を除き、`path:`付きで
  `Peg.parse`し、`kind`で`catch`する——15行ほどで`pl0.cul`や`lin.cul`と
  同じ形。共通化する価値はない。違う2行（どのモジュールを`import`するか、
  どの`kind`を`match`するか）こそが読み手にとって意味のある情報だから。

## 移植できなかったもの

型システムとして実質的な部分は、すべて「どちらの問題を解いているか」で
形が決まり、「型システム」という括りでは共通化できなかった。

- **戻り値で持ち回るものの"数"自体が違う。** `lin.cul`の`typing`は
  `(型, env')`という**1つ**の状態を返すが、`hm.cul`の`infer`は
  `(型, 代入)`という**2つ**を返し、しかも複数ステップにまたがるケースは
  次に進む前に新しい代入をそれまでの代入へ`compose`しなければ、変数の
  現在の型すら引けない。「状態を関数的に持ち回る」ための汎用ヘルパーを
  書こうとすると、持ち回るものの個数と合成のしかたを知っている必要が
  あり、それはもう設計そのものであって、道具化できる基盤ではない。
- **環境が持つ演算の集合が違う。** `lin.cul`のenvは挿入・削除・
  修飾子によるフィルタだけで足りる——一度格納された変数の型は、消費
  されるまでそのまま変わらない。`hm.cul`のenvは`apply_env`——格納済み
  の各型スキームの中身を現在の代入で書き換える処理——が要る。これはHMの
  型が格納後も変わりうるからこそ意味を持つ演算で、両方をカバーできる
  ほど汎用な「環境モジュール」を作ろうとすると「格納された値に何を
  していいか」まで汎用にする必要が出てきて、結局ただの`Object`に戻る。
- **`hm.cul`の半分は`lin.cul`に対応物が一切ない。** `apply`・`compose`・
  `unify`・`bind`（出現検査）・`generalize`/`instantiate`——これが
  Algorithm Wの本体そのもの。型を一切合成しない検査器（linz）には、
  そもそも「未知のものを解く」必要がないので共有すべきものがない。
- **消費と蓄積は逆向き。** `lin.cul`のenvは使うたびに縮む
  （`unbound`）。`hm.cul`のenvは増えるか書き換えられるだけで、決して
  縮まない。見た目は同じ`Object`でも、ライフサイクルは正反対。
- **新しい名前の生成。** `hm.cul`は新しい型変数のために、モジュール
  レベルの`mut next_id`というカウンタを持つ——ここだけは意図的に
  関数的に持ち回らず、他のすべての部分とは書き方を変えた。ソースに
  無い名前を合成する必要があるのがここだけだからだ。`lin.cul`には
  この種の仕組みが全くない。

## 結論

「PEG＋型推論＋VMでDSLが簡単に書ける」という標準ライブラリ化のアイデアは
成り立たない。使い回せた約2割（文法の書き方・エラーの形・`bound`という
慣用句・ドライバの骨格）は、すでに確立された流儀であるか、関数化するには
小さすぎるかのどちらかだった。残り約8割の型システムそのものは、
「どんな型システムを作るか」に本質的に依存していて、道具化すると
意味を失う。`Peg`（文法→木）と`CodeGen`（IR→VM/AOT、実演は
`examples/pl0/pl0_codegen.cul`）は既に標準ライブラリレベルで再利用可能な
部品として存在している。その間を埋める型システムだけは、culebraに
限らずどの言語でも、著者が自分で書くしかない部分なのだと思う。
