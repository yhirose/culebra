# tests/*.cul that do not pass on Windows yet, one per line.
#
# tools/check_suite_on_windows.sh runs the suite under the VM executor and
# holds the failing set to exactly this list: a new failure fails the job, and
# so does an entry that starts passing (delete it in the same commit that fixes
# it). Everything not listed here must pass — which is the point, because until
# 2026-08-28 the Windows lanes ran 6 of the 215 files and a registration that
# died in the clang/lld switch went unnoticed (see include/wrap.h).
#
# Grouped by cause, so the list reads as a work list rather than a tally.

# --- FS.abspath's dot-collapse on an already-rooted, driveless input ---------
# `is_abs` is settled (user decision, 2026-08-28): match std::filesystem's
# Windows definition (a root-name/drive is required) rather than loosen it,
# and the test is fixed to assert on Sys.getcwd() instead of a hand-written
# "/tmp". What's left is three FS.abspath cases built the same way
# ("/tmp/./a/../b" etc.) — absolute() has to promote a driveless root to the
# current drive before lexically_normal can run, an interaction this cycle's
# normpath fix (a plain relative input) didn't exercise and isn't verified
# for. Rewriting them off Sys.getcwd(), the way the two lines right after
# them already are, is the likely fix — not done here without a Windows run
# to check it against.
tests/test_fs.cul

# --- a file still open cannot be removed -------------------------------------
# `FS.remove` answers "The process cannot access the file because it is being
# used by another process" — Windows refuses while a handle (or, for
# SharedBuffer.file, a mapping) is open, where POSIX unlinks regardless.
# SharedBuffer.file's own CreateFileA is fixed (FILE_SHARE_DELETE, matching
# fswatcher.h's). File.open goes through std::fstream, which has no portable
# way to ask for share-delete — fixing it means opening via a native HANDLE
# and wrapping it, not a one-line flag; that is its own change.
tests/test_file.cul

# --- FS.watch delivers something, but a later expectation reads false --------
# The startup race is fixed (platform_start now waits for the first
# ReadDirectoryChangesW post — see fswatcher.h) and the file no longer hangs:
# it fails fast with `assert_true failed: value: false` instead of running to
# the step's 60s timeout. Which of the file's ~15 assert_true calls that is
# does not show in the message (unlike assert_eq, assert_true reports no
# left/right, no position) — narrowing it needs either a diagnostic run with
# prints between sections, or position info on assert_true's own failure,
# which is a change of its own. Real progress; not yet root-caused.
tests/test_fs_watch.cul

# --- native behaviour that differs, one test each ----------------------------
# Proc: `Proc.run(["sh", "-c", "kill -TERM $$"])` (self-signal via a POSIX
# shell) has no Windows equivalent — MSYS's bash emulates the signal itself
# and TerminateProcess-based decode_child never inspects the exit code for
# it, so `code`/`ok`/`signal` all read differently than POSIX's waitpid
# decode. The *runtime's own* timeout-kill (`Proc.run(cmd, timeout:)`) is
# fixed (`decode_child` now sets `signal: "SIGKILL"` when it terminates a
# child itself) — what's still open is this one shell-self-kill probe, which
# would need a Windows-native way to signal-and-detect, not a decode fix.
tests/test_proc.cul
# Sys: `Sys.set_env(name, "")` doesn't create an empty-valued variable on
# Windows — `_putenv_s`/`SetEnvironmentVariable` both DELETE the variable
# when given an empty value (documented Win32/CRT behavior; no workaround
# through the standard API), so the "empty vs unset" distinction
# `Sys.env(name, nil)` relies on cannot exist on this platform. Not a bug.
tests/test_sys.cul
